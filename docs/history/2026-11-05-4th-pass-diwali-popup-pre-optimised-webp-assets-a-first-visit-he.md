# 2026-11-05 (4th pass) — Diwali popup: pre-optimised WebP assets + a first-visit `<head>` preload

> Session-history detail. Index: [docs/HISTORY.md](../HISTORY.md)

---

| Area | Detail |
| :--- | :--- |
| **Brief** | Owner: *"now only thing left is loading speed and optimisation, rest document and push to origin."* |
| **Asset pipeline** | `sharp` 0.35.5 (already in `node_modules`) re-encoded the two artworks **once** into static WebP files, committed as real assets: **`public/diwali-popup-square.webp`** 1024×1024, **110 KB** (from `public/diwali template 2026.png`, 1080×1080 / 2.1 MB) and **`public/diwali-popup-wide.webp`** 1792×896, **139 KB** (from `public/diwali.png`, 1920×960 / 850 KB). Both are exactly 2× their largest CSS box, so nothing is upscaled. Command used: `sharp(...).resize(w, h, { fit: 'inside' }).webp({ quality: 78 \| 76, effort: 6 })`. |
| **Why not `next/image`'s optimizer** | `<Image unoptimized>` now points straight at those files. Routing a *already final* WebP back through `/_next/image` only re-encodes it, and the old path made every cold request read + resize a 2.1 MB PNG server-side before a byte could leave. The static files are covered by the existing `immutable, max-age=31536000` header rule, so repeat visits are a cache hit with zero compute. |
| **First-visit preload** | The popup is a **client** component — it cannot render (or even be known to be needed) until hydration, because "first visit" lives in `localStorage`. So `app/layout.tsx` now emits a **457-byte inline `<script id="diwali-preload">` in `<head>`**, which runs during HTML parse and appends `<link rel="preload" as="image" type="image/webp" fetchpriority="high">` **only** when `svd_diwali_2026` is unset and the path is not `/checkout` or `/demo`. Returning visitors never create the link — the cost is one `localStorage` read. |
| **Single source of truth** | **NEW `lib/diwali-popup.ts`** (pure constants, no React, no browser API at module scope) holds the storage key, the 768 px query, the skip paths, the two art objects and `buildDiwaliPreloadScript()`. The server layout and the client component import the same strings, so a preload `href` can never drift from the `<img>` `src` — drift would mean **two** downloads of the same artwork. The generated script was syntax-checked with `new Function()` (457 chars, OK). |
| **Deliberately NOT done** | No AVIF `<picture>` (WebP is universal, 110 KB is already small, and a second format doubles the preload-matching surface); no DPR `srcset` (a 1024/1792 file at 2× covers the caps, and a plain `src` is what makes the exact-URL preload safe); no server-side first-visit detection (a cookie read in the layout would force dynamic rendering site-wide). |
| **Files** | `app/components/DiwaliPopup.tsx` (uses `unoptimized`, no `sizes`), `lib/diwali-popup.ts`, `app/layout.tsx` (`<head>`), `app/(site)/layout.tsx` (mount), the two WebPs. `public/diwali.png` is **byte-for-byte untouched** — it is embedded cross-origin per the 2026-11-04 rule and served `immutable`, so changing it would not propagate. |
| **Master committed** | `public/diwali template 2026.png` (the 2.1 MB square master) was first left untracked, then **committed on the owner's explicit request** (same session). WHY worth the 2.1 MB: it is the *source* of `diwali-popup-square.webp`, so without it a fresh clone / a different machine could not regenerate the artwork, and the master would live on exactly one laptop. Nothing references it at runtime — it is a source file that happens to sit under `/public` (the popup loads only the WebP). `public/diwali.png` stays committed too, both as the wide master and because external embeds use it. |
| **Verification** | Standing single-pass directive honoured — no build, dev/start server, typecheck or `check:*` suite. The preload script string was parsed with `new Function()`; both WebPs were re-read with `sharp().metadata()` to confirm 1024×1024 / 1792×896 and their sizes. |
