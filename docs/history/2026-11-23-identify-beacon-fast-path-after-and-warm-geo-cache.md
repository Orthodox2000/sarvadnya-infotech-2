# 2026-11-23 — `/api/identify` fast path: geo/rdns via `after()`, warm geo cache, lean cold start

> Session-history detail. Index: [docs/HISTORY.md](../HISTORY.md)

---

| Fact | Detail |
| :--- | :--- |
| **Ask** | Owner: *"/api/identify is taking too long with 36 invocations and 8s, smoothen it and make it faster"*. This follows the 2026-11-20 report where the same route used 3.46 s Active CPU across 13 hits; the early bot/ignored-IP exit added then did not solve the cost for genuine visitors. |
| **Root cause — inline enrichment** | A new or 30-day-stale session waited for the whole enrichment chain before the 204: `recordVisitor()` upsert → `lookupGeo()` (`ip_cache.findOne` → up to 2.5 s `ipwho.is` HTTP call → `ip_cache.updateOne`) → `applyGeo()` (`visitors.updateOne`) → fire-and-forget reverse DNS with up to 3 s timeout. None of it is needed by the caller — the response is a bare 204 — and the visitor document is already committed by `recordVisitor()`. |
| **Root cause — cold start** | `ensureVisitorIndexes()` awaited **six** serialised `createIndex` round trips on every cold function start, even though the indexes persist in MongoDB after the first-ever call. The client-side `VisitorProvider` already throttles to one beacon per 10 s per tab, so 36 invocations are genuine traffic, not a client bug. |
| **Fix 1 — post-response enrichment** | `app/api/identify/route.ts` now imports `after` from `next/server` (stable in Next 15.5.29, already used by `/api/cart/order`) and moves `lookupGeo` + `applyGeo` + `lookupReverseDns` + `applyReverseDns` into a single `after()` callback. The 204 returns as soon as the session upsert commits. `applyGeo()` is still called when `geo` is `null` so `geoAt` is stamped and failed lookups are not retried on every beacon. The callback is fully `try/catch`-ed: a frozen function or failed provider leaves only enrichment missing, never the visit. |
| **Fix 2 — warm geo cache** | `lib/visitors.ts` gains a module-level `geoMem` Map (per Vercel function instance, TTL-matched to `GEO_TTL_MS` / `NEGATIVE_TTL_MS`, capped at 2000 entries with oldest-first eviction) and a `geoInFlight` single-flight Map. Warm repeat IPs answer from memory with zero Mongo/HTTP work; simultaneous beacons for the same IP share one promise instead of each hitting `ipwho.is`. Negative results are cached for the existing 1 h window so a dead provider is not retried per beacon. |
| **Fix 3 — lean cold start** | `ensureVisitorIndexes()` now awaits only the unique `{ sessionId: 1 }` index, which is required for the upsert's dedup correctness. The other five (`lastSeen`, `geo.country`, `visitCount`, `ip_cache.ip`, `ip_cache.expireAt` TTL) are created in a backgrounded, memoised promise with a logged catch — they are admin query / cache performance only, and already exist in production. A cold beacon now commits after one `createIndex` + one `findOneAndUpdate`. |
| **What is unchanged** | Beacon payload contract, rate limit, bot/ignored-IP early 204, origin security checks, `maxDuration: 10` / `memory: 1024`, visitor schema, admin queries, client `VisitorProvider` throttling, and every other route calling `lookupGeo()` (it keeps the same `{ geo, cached }` return shape). No Mongo document shape changed. |
| **Verified** | Standing single-pass directive (root AGENTS §3): no build, dev server, typecheck or check suite run — the owner did **not** request one for this change (the previous change's build result is in the 2026-11-23 Fluid CPU entry). Static review: `after` export confirmed present in `node_modules/next/server.d.ts` on Next 15.5.29 and already used in `app/api/cart/order/route.ts`; `toDateMs(undefined)` returns `NaN`, so the cache-hit guard is safe. Deploy, then re-check the Vercel function chart: the inline 2.5 s HTTP + 2 extra Mongo writes should be gone from the beacon's critical path; geo/rdns still land on the visitor document within the post-response window. |
