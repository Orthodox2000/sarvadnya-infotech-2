| **Ask** | Owner: *"we are in a period of high priority as cpu usage is near 85% for month, and yesterday was peak, what seems to be issue and what is real source, tell what data u need to identify as even last 7 days we have 60% edge request"* and *"can we just create newsbar complete static, hardcode in internal array and remove dependency from db for it, same for reviews and other entities for homescree, just comment db fetched data so it will not be needed, hardcode stuff on homepage and also hardcode contacts and footers content"*. |
| **Code-level diagnosis** | The (site) layout ran `getSettings()` + `getNews()` on **every site page**; `/` then ran four more reads (`getPartners`, `getReviews`, `getContent('home_faq')`, `getSettings`). `NewsFeed`, `CustomerReviews`, `CertifiedPartners`, `FAQ`, `Footer` and `SupportButton` each had a mount-time `/api/*` fallback fetch, and `/contact` fetched `/api/settings`. That is up to **7 server/client reads per visit**, before the still-live `/api/identify` beacon. Prior mitigations (`unstable_cache` on `getNews()`, CDN `PUBLIC_API_CACHE`, after()-deferred geo/RDNS) were already in place, so the residual CPU was the remaining per-request work plus traffic volume — not the newsbar alone. |
| **Real source — open** | Code inspection cannot decide between Vercel Edge/Fluid CPU, Function invocations, Atlas CPU and RUM beacon volume. The telemetry list requested from the owner: Vercel CPU/invocations **by path and runtime**, Edge vs Function split, cache hit ratio, cold starts/concurrency, top routes (7 d), RUM network waterfall, Atlas CPU/ops/slow queries/top collections, and `/api/identify` logs with bot-vs-human and 429 counts. No dashboards, logs or DB dump were supplied in this session. |
| **Data provenance** | `MONGODB_URI` in `.env` is the live cluster. A **read-only** snapshot script (`/tmp/opencode/read-live-content.mjs`, outside the repo) captured settings (25 keys), `site_content.home_faq`, 15 news items, 4 reviews, 9 partners and 6 modules into `/tmp/opencode/live-static-data.json`. Only public fields were copied into the repo; GROQ/GEMINI keys, recipient maps and CC config are deliberately excluded. |
| **Change — snapshot module** | New `lib/static-site-content.ts` exports `STATIC_NEWS` (12 ticker items: title/description/slug/date only), `STATIC_REVIEWS` (the 4 live reviews, real ratings only), `STATIC_PARTNERS` (canonical brand row), `STATIC_HOME_FAQ` (21 live Q&As), `STATIC_SITE_SETTINGS` (13 public contact/social/map fields) and `STATIC_FOOTER_MODULES` (6 live id/title pairs). Nothing invented. Each array has a `CHANGE: 2026-11-25` comment with the trade-off. |
| **Change — server routes** | `app/(site)/layout.tsx` is now a **sync** component: `getSettings()`/`getNews()`/`getSettingsData()`/`normaliseSettings()` removed; `STATIC_NEWS` feeds `NewsFeed`, `STATIC_SITE_SETTINGS` feeds `SupportButton`. `app/(site)/page.tsx` is now sync: the four DB reads are left as a commented block per the owner's instruction and replaced by the snapshot constants. `app/(site)/contact/page.tsx` uses `STATIC_SITE_SETTINGS`; `fetchSettings()` removed (form POST untouched). |
| **Change — client components** | Removed mount-time fetches and loading skeletons from `NewsFeed` (`/api/news`), `CustomerReviews` (`/api/reviews`), `CertifiedPartners` (`/api/partners?type=brand`), `faq.tsx` (`/api/content?section=home_faq`), `Footer` (`/api/settings` + `/api/modules`) and `SupportButton` (`/api/settings`). Footer module links still come from `moduleHref()` and now use the snapshot rows; the rating wall still uses `normalizeRating()`; no `aggregateRating` was introduced. |
| **Trade-off (owner accepted)** | Admin edits to news/reviews/FAQ/partners/contact settings no longer reach the homepage, ticker, footer or contact page until `lib/static-site-content.ts` is regenerated. The API routes, sitemap, search and Sara are untouched and still read the DB; sitemap/news pages remain cached as before. To refresh, re-run the read-only snapshot and replace the arrays. |
| **NOT fixed by this pass** | `VisitorProvider` still POSTs `/api/identify` on page load/path change; `VisitorProvider`, Analytics, SpeedInsights and GTM remain mounted. If the 60% edge figure is beacon/middleware volume, this change will not move it — that needs the telemetry above before disabling or throttling anything. |
| **Verification** | None run. Owner did not ask for a build/lint/test in this session (single-pass directive §3). Manual second pass caught and removed one stale `loading` reference left in `CustomerReviews`' IntersectionObserver effect. Deploy first, then compare Vercel CPU-by-path and Atlas ops before/after. |
