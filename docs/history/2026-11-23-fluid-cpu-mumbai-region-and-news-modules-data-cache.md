| **Ask** | Owner: *"my fluid cpu is near exhaustion and your previous changes have barely made any impact, check and insure we are heavily caching news and modules as they are commonly and never changed"*, then *"do and implement as our 98% customers are from india"*, then step 1: *"Check vercel.json and code: Make sure `regions: [\"bom1\"]` isn't overridden elsewhere"*. Owner supplied the Vercel Fluid CPU-by-region report: `iad1` 1 h 51 m / 54.9%, `bom1` 18 m / 9.0%, `sfo1` 27 m / 13.7%, `sin1` 20 m / 10.1%, `fra1` 14 m / 7.0%, `lhr1` 8 m / 4.0%, `gru1` 2 m / 1.2%, `syd1` 18 s / 0.1%. |
| **Finding — region** | Neither repo had a `"regions"` key anywhere. A repo-wide grep for `"regions"`, `--regions`, `VERCEL_REGION` and `regions:` returned **zero matches** in JSON/JS/MJS/TS/TSX/YAML/MD/SH. `next.config.js` has no region knob; the only runtime declarations are `export const runtime = 'nodejs'` on API routes (runtime, not region). Nothing in code or config overrides Vercel's project default of `iad1` (Washington, D.C.), which is exactly the 54.9% bucket. |
| **Reading the region report** | Node functions were running in `iad1` (the default), so the 18 m in `bom1` plus the `sfo1`/`sin1`/`fra1`/`lhr1`/`gru1`/`syd1` buckets (~36% combined) are **Routing Middleware**, which Vercel deploys to all regions regardless of the Function Region setting. Pinning `bom1` moves the function bucket (54.9%) to Mumbai; it does **not** remove the global middleware bucket. Narrowing `middleware.ts` further is a separate, deliberate change — it was intentionally not bundled into this pass. |
| **Region fix** | Added `"$schema": "https://openapi.vercel.sh/vercel.json"` and `"regions": ["bom1"]` to **both** `vercel.json` files: the public frontend and the nested admin fork (`sarvadnya-advanced/vercel.json`). The existing `functions` block for `app/api/identify/route.ts` (`maxDuration: 10`, `memory: 1024`) is untouched. `bom1` = Mumbai, `ap-south-1` (Vercel's region list). `regions` in `vercel.json` overrides the dashboard Function Region on the next deployment. Both deployments serve Indian customers, so both were changed. |
| **Finding — caching** | The 2026-11-20 pass had already added CDN caching (`PUBLIC_API_CACHE` = `s-maxage=3600`) to `/api/news`, `/api/modules`, `/api/search` etc. and ISR (`revalidate = 3600`) to `/news/[slug]` and `/modules/[slug]`. What remained: **every uncached render or cold function still ran the full Mongo work**. `fetchNews()` does `find({}).toArray()` + `enrichNews()` (which splits every article body for reading time) + a full sort. A single article render called that via `generateStaticParams()`/`generateMetadata()`/the page and then ran `getNewsBySlug()` (another full scan) and `getRelatedNews()` (a third query). `getModules()` was re-run independently by the layout, sitemap, search, `/api/modules` and module pages. |
| **Caching fix** | `lib/mongodb-utils.ts` now imports `unstable_cache` from `next/cache`. `getNews()` and `getModules()` are `unstable_cache(...)` wrappers with keys `public-news-v1` / `public-modules-v1`, `tags: ['news']` / `['modules']` and `revalidate: 3600`. The cached values are already JSON-serialisable (`serializeData()`), so they are safe for the Data Cache. `getNewsBySlug()` now does an in-memory `find()` over the cached enriched list instead of a second full-collection scan; `getRelatedNews()` derives its cards from the same cached, newest-first list and strips `content` at the end (retired slugs and derived reading times remain applied). |
| **TTL decision** | The Data Cache TTL deliberately **matches** the owner's previously accepted 1-hour CDN/ISR window (2026-11-20 entry). It is not stretched to 24 h: admin-added news/modules must still appear within the hour, and no cross-repo revalidation webhook exists by the owner's ruling. The CPU saving comes from eliminating repeat Mongo scans inside every uncached render — not from making content staler. |
| **What is unchanged** | No page markup, SEO metadata, breadcrumb/JSON-LD output, hydration boundary or client component changed. `/api/news` and `/api/modules` keep `PUBLIC_API_CACHE`; the two detail pages keep `revalidate = 3600` / `dynamicParams = true`. The nested repo's `lib/mongodb-utils.ts` was **not** touched — admin screens must always read fresh data. |

The `unstable_cache` wrappers and the `bom1` config produced no type/build errors; `/news/[slug]`, `/modules/[slug]`, `/news`, `/modules`, `/api/news`, `/api/modules`, `/api/search` and `/sitemap.xml` all built with their expected 1 h revalidate. Only warning is a **pre-existing** `postcss-url-parser: Unable to find uri in 'background-image:url()'` notice in `app/globals.css`, unrelated to this change. Repo-wide grep confirmed no other region declaration in either tree.
