# 2026-11-16 (fourth session) — Footer social icons dead: raw settings map vs snake_case, and the Facebook URL

| Fact | Detail |
| :--- | :--- |
| **Report** | Owner: *"footer social media links dont work and facebook lnk is wrong"*, supplying the live profile URL `https://www.facebook.com/people/Suman-Sawant/pfbid02fQZB9QyH59fPFffaWDfHKWhpp9mZjBSKN5x3T2zYUbgcpWW49LDAAy8Eiutqfs97l/`. |
| **Root cause (links "not working")** | `getSettings()` returns the **raw settings map** whose keys are the document keys (`NEXT_PUBLIC_FACEBOOK_URL`, …). `app/(site)/page.tsx` passed that map straight into `<Footer settings={settingsData} />`, while `Footer` reads `settings.facebook_url`. Every lookup was `undefined`, so the icons rendered **`href="#"`** — and because the prop was **truthy**, Footer's own `/api/settings` fetch never ran, so the homepage links stayed `#` **permanently**. Other pages (no prop) fetched client-side and worked, but showed `#` until hydration. `app/(site)/layout.tsx` had the same defect for `SupportButton`, so the floating WhatsApp button fell back to the **support** number (9821309060) instead of the configured WhatsApp number (9870942557). |
| **Fix** | New **`lib/site-settings.ts`** — `normaliseSettings()` accepts either shape (raw uppercase map or snake_case) and returns the snake_case shape, or **null** when nothing is recognised (so the client fetch still runs on an empty settings collection). Wired into `app/(site)/page.tsx` (Footer + FAQ) and `app/(site)/layout.tsx` (SupportButton). `Footer` normalises the prop itself too, so a future caller cannot reintroduce the mismatch. |
| **No more `#`** | `Footer`'s social links now fall back to the real destinations (`process.env.NEXT_PUBLIC_*`, then an inlined constant), so the server HTML already carries working URLs — no flash, and they work if `/api/settings` is slow or JS is off. The icon anchors gained `aria-label` (they were icon-only with no accessible name) and `aria-hidden` on the SVGs. |
| **Facebook URL (the wrong link)** | `facebook.com/sarvadnyainfotech` resolves to a Facebook **error page**. Updated in **`.env`**, **`.env.example`**, the Footer fallback constant, the two `sameAs` arrays in **`lib/seo.ts`** (Organization + LocalBusiness structured data), and — the one that actually serves production — the **live `settings` collection** (`NEXT_PUBLIC_FACEBOOK_URL` was an empty string, so `/api/settings` was falling through to the Vercel env value). Verified: `GET https://www.sarvadnyainfotech.com/api/settings` now returns the new pfbid URL. Instagram / LinkedIn / YouTube were already correct and were left alone. **Not changed:** `email-signature.html` and the nested admin repo still carry the old Facebook URL. |
| **Not touched** | No prices, cart, checkout, email or Sara code. The admin panel (nested repo) keeps its own settings screen; it reads the same key, so no admin change is required. |
| **Verified** | Standing single-pass directive (§3): no build, dev server, typecheck or `check:*` suite. Live `/api/settings` was probed before/after the DB write; the previous dead page and the three working profiles were HTTP-probed. |
