## ✅ The fix

New exports in `lib/visitors.ts`:

- `isIgnoredIp(ip)` — loopback is **always** ignored in every environment (production traffic arrives over the internet, so a loopback peer can only be a local process), plus an exact match against `VISITOR_IGNORE_IPS`.
- `isIgnoredRequest(request)` — convenience wrapper for route handlers.
- `getIgnoredIps()` — returns the parsed configured list.

`VISITOR_IGNORE_IPS` is comma-separated, trimmed, lower-cased, bracket-stripped and parsed **once at module load**.

Gate points:

| Location | What it does |
| :--- | :--- |
| `recordVisitor()` | returns `{created:false, needsGeo:false}` **before** any DB call — the only `visitors` writer |
| `lookupGeo()` / `lookupReverseDns()` | return empty, so no ipwho.is call and no `ip_cache` write |
| 5 form entry points | return `200 {ignored:true}` **before** saving and **before** `sendEmailDirect()` |

`192.168.*` is deliberately **not** auto-ignored: it is already excluded from enrichment, and silently dropping the whole private range would change production behaviour for no benefit. The specific addresses are listed instead.

# THREAD B — `ConsentBanner` → temporary hover pill

Continued from `2026-09-30.md`, where the component was left as v2 (a bottom-right card). The owner resolved the open `SupportButton` collision question with: *"make it a temporary hover button which disappears after 5 seconds, zindex top."*

- **Expanded state** is `div#cookie-notice-panel` with the single sentence *"Our website uses cookies to make your experience better!"*, a teal **Learn more** link to `/privacy`, and a dismiss X. `AUTO_COLLAPSE_MS = 5000`.
- Opens on `mouseenter` / focus / tap; auto-collapses 5s after the pointer leaves **and** 5s after a tap.

### 🐛 Real bug caught only because the harness used a genuine touch profile

A touch tap fires no mouse events of its own — the browser synthesises them right after `touchend`:

```
pointerdown → touchstart → touchend → mouseover → mouseenter → mousedown → click
```

A naive `onClick={() => (open ? close() : open())}` therefore read `open === true` (the synthetic `mouseenter` had just set it) and immediately shut the card again. Instrumenting the pill proved the tap produced a **genuine `click`** on the button and the card **still never appeared** — the feature was **100% broken on phones**, the main audience. Fixed by snapshotting intent in `onPointerDown` and toggling off an `openBeforeBurst` ref, not off the `open` state.

A **second related bug**: a touch never fires `mouseleave`, so the 5s countdown was never armed on a phone and the card sat open until the next navigation. The click handler now arms the timer itself.

### Verification — 104/104, twice

Measured card lifetime **4912ms / 4926ms** against a 5000ms target. Covered auto-hide, hover, real `touchscreen.tap`, mouse, geometry at 6 viewports, exact copy, `/privacy` navigation, dismissal persistence, reduced-motion, and hit-testing of pill / Learn more / dismiss.

The resting pill clears the `SupportButton` stack by **8px** (360×640) to **52px** (1920×1080). The expanded panel is `z`-above it per the owner's instruction, but the Ask AI button stays **clickable** at all 6 viewports (the panel does not reach its centre).

4. **Same-frame click** — `page.click()` presses before React flushes the hover state. Proven a harness artifact with a human-paced hover-then-click, which closes correctly.

# THREAD C — `excel logs.csv` was silently corrupt

## Context

Appending today's rows to `daily logs/excel logs.csv` surfaced a validation failure: the file did not parse. Investigating rather than appending blindly found **two pre-existing defects**, one of them three months old.

## ⛔ Defect 1 — an unterminated quoted field on `23-06-26` (the serious one)

The `23-06-26` row opened a quoted field and **never closed it**. Its description ends `...replaced 'Navi Mumbai' with 'Mumbai' in hero title.` with no closing `"`.

Under RFC 4180 that leaves the parser *inside* a quoted field for the remainder of the file, so every subsequent row is absorbed into that one field instead of parsing as its own `DATE,PROGRESS` row.

| | |
| :-- | :-- |
| Rows before | **27** (1 header + 26 data) |
| Rows after | **77** (1 header + 76 data) |
| Recovered | **50 rows**, `24-06-26` → `01-10-26` |
| Broken since | **2026-06-23** — roughly three months of July / August / September logs |

The last "row" parsed before the fix had **809 fields**, which is the signature of this failure: the `DATE` values of all 50 swallowed rows had migrated into the `PROGRESS` column.

## ⛔ Defect 2 — a stray blank line

One `\r\n\r\n` between the `10-08-26` and `14-08-26` rows parsed as a row with a single empty cell. Removed.

## ✅ The repair

Both fixes are surgical and were **validated before writing** — the repair script ran the parser on the in-memory result and aborted without touching the file if anything still failed. That guard is what caught Defect 2 on the first attempt.

- **Defect 1:** insert the single missing closing `"` at the end of the `23-06-26` description. Verified the anchor `in hero title.\r\n24-06-26,` occurs **exactly once** in the file, and that the replacement was a **1-byte insertion**, before applying it.
- **Defect 2:** remove the one blank line, only after confirming exactly one occurrence existed.

File conventions preserved and re-asserted: UTF-8 **BOM** kept, **CRLF** only (0 bare LF), **no trailing newline** on the final line, date format `DD-MM-YY`, whole description quoted with internal `"` escaped as `""`. Net: 86 607 → 86 606 chars (+1 quote, −2 for the blank line).

**4. Razorpay's official SDK requires Node ≥ 22.2; this machine runs Node 20.18.1.** Confirmed against Razorpay's own prerequisites page. The package declares no `engines` field, so `npm i razorpay` succeeds *silently* on Node 20 — the incompatibility would only surface at runtime. The project also declares no `engines`, so **Vercel deployment is unaffected**; only local `next dev` is exposed.

**5. Client-supplied totals are attacker-controlled.** The order route must recompute every amount from a server-side catalog by product id. Locked into the design so the test scaffold does not teach the wrong pattern.

**6. `app/demo/` and `app/(site)/demo/` collide.** Both resolve to `/demo`, which is a hard Next.js build error — so "isolated page" and "flush current structure" are the same action, not two.

Two further issues were folded into the design rather than treated as blockers: local runs write to the **production** MongoDB (AGENTS.md + Thread A), so order persistence needs the `isIgnoredRequest()` gate; and `/demo` is `noindex` via metadata but **not** in `app/robots.ts` disallow, which is the weaker protection.

## ✅ Razorpay research — official SDK and docs

Verified directly against Razorpay's documentation rather than assumed:

| Fact | Detail |
| :-- | :-- |
| Official SDK | `razorpay@2.9.8` — MIT, `razorpay/razorpay-node`, 414k weekly downloads, published 2026-07-15 |
| Dependencies | exactly one: `axios@^1.18.1` |
| Node requirement | ≥ 22.2 (docs), no `engines` field (package) |
| Create order | `POST https://api.razorpay.com/v1/orders`, HTTP Basic auth, `{ amount, currency, receipt, notes }` |
| Amount | **paise** (`50000` = ₹500); must match the checkout option **exactly** |
| `receipt` | max 40 characters |
| **Order reuse** | **prohibited** — an `order_id` maps 1:1 to a payment attempt; reusing it after a failure errors |
| Checkout script | `https://checkout.razorpay.com/v1/checkout.js` — **never self-host**; open **only on user action** |
| Callback style | SPAs use the JS `handler`, receiving `razorpay_payment_id`, `razorpay_order_id`, `razorpay_signature` |
| Signature | HMAC-SHA256 over `{order_id}\|{payment_id}` keyed by the secret, `crypto.timingSafeEqual` |
| SDK helper | `validatePaymentVerification({ order_id, payment_id }, signature, secret)` |
| Test mode | keys must start `rzp_test_`; test card `4111 1111 1111 1111` |

Go-live checklist items adopted into the design: verify server-side, source `order_id` from the server DB not the client callback, fulfil only after verification, timing-safe comparison, store `razorpay_payment_id` for idempotency, never expose or log the secret.

**Known limitation, documented rather than hidden:** there is **no webhook**, because a webhook needs a public HTTPS URL and nothing is being deployed. The success page is therefore client-verified only and is explicitly **not** production-grade order confirmation.

## ⚠️ The `npm update` vs `--latest` trap

The owner asked to "update rest packages". `npm outdated` shows why that needed qualifying:

| Package | Current | `npm update` → Wanted | `--latest` → Latest | Verdict |
| :-- | :-- | :-- | :-- | :-- |
| `next` | 15.5.26 | 15.5.27 | **16.3.8** | Major 15→16 |
| `typescript` | 5.9.3 | 5.9.3 | **7.0.2** | Major ×2 (Go rewrite) |
| `mongodb` | 7.7.0 | 7.7.0 | **6.21.0** | ⚠️ `latest` is *older* — would **downgrade** |
| `@types/node` | 20.19.43 | 20.19.43 | 26.6.3 | types/runtime mismatch |
| `react`, `react-dom` | 19.2.4 | 19.2.4 | 19.3.0 | minor, safe |

`npm update` applies only semver-compatible bumps — a `next` patch and a `shadcn` patch. `--latest` would jump Next to 16.3.8 and TypeScript to 7.0.2 across 100+ files on a machine with **1.8 GB free**, and would actively **downgrade `mongodb` to 6.21.0**. The plan therefore specifies `npm update` only, with Next 16 and TypeScript 7 explicitly out of scope.

## ✅ The permanent guard (the part that makes the fix durable)

A one-time cleanup would rot. The design makes independence **enforceable**: `scripts/check-demo-independence.mjs` greps `app/`, `lib/` and `components/` for `/demo` outside the demo folders and exits non-zero on a hit, wired as `npm run check:demo` and into `npm run test:all`. ## 🗺️ Design decisions worth recording

- **`lib/demo/catalog.ts` + `cart.ts` are framework-free** on purpose, so plain `node` can test them — the same pattern as the existing `scripts/sara-topics-test.mjs`. All arithmetic in **integer paise**, never floats.
- **The Razorpay seam is one file** (`lib/demo/razorpay.ts`), so hardening or replacing the gateway later touches exactly one module.
- **The CSP change is unavoidably site-wide.** Next *merges* header rules rather than replacing them, so a `/demo/:path*`-scoped header cannot remove a global directive. It is purely additive — no existing directive removed or narrowed.
- **Pages stay in `(site)/demo`** per owner decision, so the demo inherits the real navbar, support button and visitor tracking. Recorded as a deliberate choice, not an oversight.
- **`localStorage` must be read in `useEffect`, never during render** — the `ConsentBanner` hydration bug from Thread B is the precedent.
- The SDK instance is created **lazily**, never at module scope, so importing the file without keys cannot throw during `next build`.
