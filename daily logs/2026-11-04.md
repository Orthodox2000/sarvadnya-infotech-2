## Session 1 — `/diwali.png` allowed to load on other origins (CORS + CORP override)

Owner brief (verbatim):

- *"Diwali image needs to load outside the website."* (relayed with the intended header shape: a `headers()`
  rule sending `Cross-Origin-Resource-Policy: cross-origin` + `Access-Control-Allow-Origin: *`)

The asset itself was uploaded by the owner through the GitHub web UI (`25a7f7e`, 11:49) — `public/diwali.png`
replaced, **6,754,815 → 850,052 bytes**, still **1920×960** PNG. Pulled fast-forward at 12:00. No code from
the owner's upload; the only local change is the header rule.

### §1 — Why the file being public was not enough

The global `/(.*)` rule in `next.config.js` sends `Cross-Origin-Resource-Policy: same-origin`, so a
cross-origin `<img>` pointing at `/diwali.png` is blocked by the browser even though the file is served
publicly. Next **merges** header rules instead of replacing them, so relaxing one asset needs a second rule
that sets the same key.

### §2 — Change

`next.config.js` `headers()`: new `{ source: '/diwali.png' }` rule immediately **after** the `/(.*)` block,
carrying `Cross-Origin-Resource-Policy: cross-origin` and `Access-Control-Allow-Origin: *`.

Order is load-bearing — `resolve-routes.js` applies matches with `resHeaders[key] = value`, so the later rule
must overwrite the global `same-origin` value; moving it above `/(.*)` would silently re-break the image.
Scoped to this one asset on purpose; nothing else on the site loosens CORP.

**Not covered (deliberate):** the Next image-optimizer URL (`/_next/image?url=%2Fdiwali.png&w=…`) does not
match this rule (`headers()` cannot match a query string without `has`). Cross-origin embeds must use the raw
`/diwali.png` path.

### §3 — Verified live after deploy

```
$ curl -sI https://sarvadnyainfotech.com/diwali.png
HTTP/2 200
access-control-allow-origin: *
cross-origin-resource-policy: cross-origin
content-type: image/png
content-length: 850052
```

`content-length` matches the new file byte-for-byte, so the deployed asset is the owner's upload and both
relaxed headers are winning over the global `same-origin` rule.

## Session 2 — Careers email: silent resume saves, per-category CC, one brand, referrer named

Owner brief, in one message:

- saving a resume must send **no email at all** (not to HR, not to the candidate, and never the global CC);
- the global CC must stop applying to everything — each email config needs a **tick mark**, and only a
  ticked category may trigger it;
- every email format must share the same branding, logo, header and footer;
- the referral signup welcome mail must **name the person attached to the referral code**.

### §4 — Resume upload is deliberately silent

`app/api/auth/careers/resume/route.ts`: the whole email block (company copy + candidate confirmation, which
rode `sendEmailDirect` and therefore also the global CC) was **removed**, along with the now-unused imports.
The route saves the Blob reference and returns `{ resumeUrl, resumeName }` only.

Job **applications** are unchanged and still notify company + candidate from `app/actions/careers.ts`.
`buildResumeCompanyHtml` / `buildResumeConfirmationHtml` stay exported for tests and back-compat even though
nothing calls them in the route.

### §5 — Per-category CC (opt-in)

New setting **`EMAIL_CC_DESTINATIONS`** (JSON array of destination keys). `getGlobalCc(destination?)` in both
repos now returns `null` unless **all four** hold: the master switch is on, the address is valid, the caller
supplies a destination, and that destination is in the list. **Empty list = no CC anywhere**, the safe default
and the behaviour of every existing install.

`sendInternalFormCopy` gained a `destination` option (explicit option → `submission.destination` →
`submission.formType`), `sendTemplatedEmail` a `ccDestination`, and `lib/email-queue.ts` forwards the stored
job destination on both the first send and the retry drain, so a retry cannot forget which category it
belongs to. The careers signup welcome passes `ccDestination: 'careers'`.

### §6 — One brand for every template

New **`lib/email-brand.mjs`** + hand-written `lib/email-brand.d.mts` (pure ESM, zero deps, the house pattern)
is the single source of the masthead (with logo), the footer band and the company block.
`lib/email-autoreply.mjs`, `lib/email-careers.mjs` (`renderShell`) and `lib/email.ts`
(`buildFormEmailHtml`, plus inline logo attachment) all render it. Company copies previously passed
`logo: null` and showed a wordmark-only header; they now fall back to the hosted `/TallyCertificate.png`, so
every careers mail carries the logo.

### §7 — Referrer named in the welcome mail

`app/api/auth/careers/signup/route.ts` looks the referrer up with `fullName` in the projection and passes
`referrerName` to `buildAccountCreatedHtml`. The template adds a body sentence — *"You joined with the
referral code `XXXX`, shared by **Name**."* — **and** a `Referred by` row in the code table, so the
person/code link survives skimming. A blank or missing name omits both (no dangling row) and every value
passes through `esc()`.

### §8 — Admin panel (nested repo `sarvadnya-advanced`, commit `60d5a46`)

- `lib/email-brand.mjs` + `.d.mts` copied **byte-identical (LF)**; its `lib/email.ts` / `lib/email-queue.ts`
  got the same destination-scoped CC and branded header/footer by hand (fork drift — never copied wholesale).
- `app/admin/email-config/page.tsx`: each destination row carries a **CC tick** (teal when ticked; while the
  master switch is off the tick is both **disabled and rendered unchecked**, so the UI can never look active
  when it is not — the stored selection is preserved and reappears when the switch is turned on). The section
  heading is now *"3 · Global CC (ticked categories only)"*, and a live summary line prints how many
  categories are ticked (or says the CC applies nowhere). Malformed JSON degrades to an empty list.
- The pre-existing uncommitted change in `app/admin/payments/summary/page.tsx` was left alone.
