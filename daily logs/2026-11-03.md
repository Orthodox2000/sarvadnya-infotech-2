### §1 — Identification (the "first business")

There were **two** definitions of the share image, and the one the owner was seeing was not the one in
`app/layout.tsx`.

| Where | What it declared | Who actually used it |
| :--- | :--- | :--- |
| `app/layout.tsx` → `metadata.openGraph.images` | `/video-thumbnail.jpg`, declared **1200×630** (a lie — the file is 1280×720) | Only routes that declare **no** `openGraph` of their own |
| `lib/seo.ts` → `OG_IMAGE_PATH` | `/opengraph-image` (the Next `ImageResponse` route in `app/opengraph-image.tsx`) | **Every page that calls `seoMetadata()`** — home, `/products`, `/news`, `/services`, `/cloud`, the whole site |

Because `seoMetadata()` returns an explicit `openGraph` object and **Next replaces** a layout-level
`openGraph` with the page-level one (it does not merge `images`), the generated card won everywhere.
Measured on the live domain **before** the change:

```
https://sarvadnyainfotech.com/            og:image = /opengraph-image  width 1200  height 630
https://sarvadnyainfotech.com/news        og:image = /opengraph-image
https://sarvadnyainfotech.com/products    og:image = /opengraph-image
```

That generated card (`app/opengraph-image.tsx`) draws a teal gradient, a rounded tile containing the
**letter "S"** — not the logo — plus the words "Sarvadnya Infotech LLP". It is rendered on demand, so there
is no file in the repo that looks like it: literally **"an image I never seen"**. That is the owner's report.

The file the owner wants already existed and is *only* used as the hero `<video poster>`:

```
public/video-thumbnail.jpg → JPEG, 1280x720, 50,022 bytes
```

It was created on **2026-09-22** as an **opaque** JPEG (flattened onto the site cream `#FBFAF6`) precisely
because Google rejects any RGBA thumbnail as "transparent" — see `daily logs/2026-09-22.md`.

### §3 — Why deleting the generated card is safe

- It was reachable **only** via the file convention and the `OG_IMAGE_PATH` literal — both gone.
- Nothing imports it (`grep` over `app/`, `lib/`, `scripts/`, `middleware.ts`, `next.config.js`: zero hits

### §4 — WhatsApp caching (what to expect after deploy)

WhatsApp caches the preview per URL, so links already pasted keep the old card until their cache expires.
The **image URL changed**, which is what forces a re-fetch on the next scrape. For an immediate check, paste
a URL with a throwaway query string (e.g. `https://sarvadnyainfotech.com/?v=2`) — WhatsApp treats it as a new
link. Google/WhatsApp also honour the `Cache-Control: public, max-age=31536000, immutable` header this repo
sets on images (`next.config.js`), so the JPEG itself must be replaced under a **new file name**, never
overwritten in place, if it is ever art-directed again.
