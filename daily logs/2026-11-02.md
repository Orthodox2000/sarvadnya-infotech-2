### §1 — The component

**`app/components/PreferredSource.tsx` (new, 87 lines).** Google's **standard declarative**
preferred-source implementation — the form Google's own Search Central reference documents, not a
hand-built API flow:

```tsx
<div google-add-preferred-source-btn data-theme="light" />
<Script id="google-preferred-source-lib"
        src="https://news.google.com/swg/js/v1/publisher.js"
        strategy="afterInteractive" />
```

| Piece | Decision | Why |
| :--- | :--- | :--- |
| The button node | An empty `<div>` carrying the bare `google-add-preferred-source-btn` attribute | `publisher.js` finds any element with that attribute and **replaces its contents** with its own localized, Google-styled button. Re-implementing the styles would drift from Google and could break the opt-in flow. |
| `data-theme` | `light` by default, overridable by prop | Every surface on this site is light. `dark` exists only so a future dark panel does not need a fork of the component. |
| `data-lang` | **Deliberately omitted** | Google then uses the reader's own browser language. Hard-coding `en` would show an English button to a Hindi or Marathi reader. |
| Script loading | `next/script`, `strategy="afterInteractive"`, fixed `id` | Loads after hydration so it never blocks first paint; the fixed id makes React dedupe if two mounts ever occur. It is mounted per surface, so it never ships on checkout, cart or demo. |
| Client-side navigation | Nothing extra needed | The served `publisher.js` bundle was fetched and checked: it contains a `MutationObserver` and the `google-add-preferred-source-btn` string, so a button mounted by an App Router client navigation is picked up. No re-init hook. |
| Fallback | Secondary text link to `https://www.google.com/preferences/source?q=sarvadnyainfotech.com` | Search Central's deeplink form. Covers a browser, extension or corporate proxy that blocks `news.google.com`, without adding a second primary CTA. |
| Layouts | `variant="card"` (house `aside` chrome) or `variant="inline"` (no chrome) | Card for page bottoms; inline for an existing panel. Only `card` is used today. |
| Accessibility | `<aside aria-label="Add Sarvadnya Infotech as a preferred source in Google Search">`, real `<a>` with `rel="noopener noreferrer"`, `focus-visible:ring-2` | Screen-reader context for the block; visible keyboard focus on the fallback link. |
| Brand | `#006569` label, `#D4EAEA` border, `#F5F4ED/60` fill, `#0f5f63` link | Teal scale only — no `green-*` / `emerald-*`, per AGENTS §2.6. |

The card copy states the benefit honestly: *more likely to appear … with a preferred badge*. It does not
promise ranking, and it invents no statistic.

### §3 — Why the standard form, not the custom or API flow

Google documents three implementations: the standard declarative button, an advanced/custom button, and a
plain deeplink. The declarative form was chosen because:

1. Google owns the visual, the localization and the account flow — nothing to keep in sync.
2. It survives Google changing the endpoint; a hand-rolled API call would not.
3. It keeps the site free of any reader identity handling. The opt-in lives in the reader's Google
   account; the site never sees who clicked.

The deeplink is kept only as a **fallback**, visually secondary, exactly as Search Central describes.

### §4 — CSP (`next.config.js`)

`publisher.js` plus its runtime and artwork need Google hosts. Every addition, and the directive it
belongs to:

| Directive | Added | Why |
| :--- | :--- | :--- |
| `script-src` | `https://news.google.com` | The `publisher.js` bundle itself. |
| `connect-src` | `https://news.google.com`, `https://accounts.google.com` | The library's runtime calls and the account surface it may query. |
| `img-src` | `https://news.google.com`, `https://*.gstatic.com`, `https://www.google.com` | Button artwork, Google's icon set, and the flow's images. |
| `font-src` | `https://*.gstatic.com` | Google's webfonts inside the button/flow. |
| `frame-src` | `https://news.google.com`, `https://accounts.google.com` | The opt-in flow can render Google's account surface in an iframe. |

`next.config.js` is the **only** place in the repo that defines a CSP (`vercel.json` has none), so there
was no second header to keep in sync. The existing `'unsafe-inline'` was already present and was not
touched.

### §11 — What the request asked for, and what Google actually allows

The request was for a top-right "Continue as …" button that fires the preferred-source opt-in **automatically,
in the backend**, so the visitor sees only Google's account popup. Three parts of that are not buildable, and
they are recorded here so nobody re-opens it later:

| Asked | Reality |
| :--- | :--- |
| "trigger preferred source button in backend" | **No server-side API exists.** Google exposes `preferredSource.addPreferredSource()` to the **browser only**. Search Central's own advanced-implementation sample wires it to a `click` listener, and states the end-user flow is unchanged. There is no endpoint to POST to. |
| "as soon as people visit … get popup" | **Browsers require a user gesture.** An opt-in fired on page load is blocked by the browser and, if forced through an interstitial, is penalised by the same Google whose badge is the goal. |
| "continue as *[their Google account]*" | We only know a name after adding Google Sign-In (OAuth client + consent screen). Showing a name beside a preferred-source opt-in implies a sign-in that is not happening — misleading consent, and exactly the pattern that puts domain eligibility at risk. **Not built.** |

No lookalike Google account screen, no auto-open modal, no hidden trigger. What shipped is Google's own button,
unstyled by us.

### §12 — The component, final shape

`app/components/PreferredSource.tsx` went from 87 lines of card to a fixed pill with **one** child: the
declarative `google-add-preferred-source-btn` node plus the `publisher.js` `<Script>`.

| Removed | Why |
| :--- | :--- |
| The heading ("Google preferred source") | Copy the owner explicitly did not want. |
| The three-sentence benefit paragraph | Same. It also named only TallyPrime/TSS/Insights while the button is domain-wide — an inaccurate scope. |
| The "Or open Google source preferences" deeplink | It was the only reason the old block needed layout space. |
| `variant="card"` / `variant="inline"` | One surface shape now; a variant prop with one caller is dead weight. |
| The `aside` wrapper and its `aria-label` | No block left to label. Google's own button carries its own accessible name. |
| The inline teal styling | Nothing of ours is rendered any more. |

Props kept: `theme` (`light` default) and `className`. Nothing else.

**The offset bug this round fixed.** The pill was positioned `top-[76px]` / `lg:top-[100px]`, but the sticky
chrome measures **88 px** on phones (NewsFeed `h-[20px]` + Navbar `h-10` + Productbar `h-7`) and **112 px** on
desktop (Navbar `lg:h-16`). The button therefore sat *underneath* the product bar and was effectively invisible.
Now `top-[92px]` / `lg:top-[118px]` — 4–6 px of clearance, never covering the logo, nav or product bar.
`z-[60]` keeps it above page content, below the header (`z-[2000]`) and below Ask Sara (`z-3000`).

### §13 — From 14 mounts to one

The original build mounted the component in 14 page files. That was wrong for two reasons: the owner said
*"homepage or any page"*, and a per-page mount means a per-page `<Script>` and a per-page maintenance point.

Now: **one mount** in `app/(site)/layout.tsx`, inside `VisitorProvider`, next to the cart drawer and the support
button. The 14 imports and JSX blocks — plus the empty `mt-10` / `px-6 pb-4` wrappers they left behind — were
deleted from:

`/modules` · `/services/tdl` · `/services/tss` · `/tally-insights` (hub, section, lesson) · `/learn-sara` (hub,
topic) · `/news` (hub, article) · `/capabilities` · `/cloud` · `/do-more` · `/tutorials`

**`app/components/PreferredSourceGate.tsx` (new, ~35 lines, `"use client"`).** Reads `usePathname()` and returns
`null` on `/checkout`, `/demo` and `/cart` (segment-exact — a bare `startsWith('/cart')` would swallow a future
`/cartoon`-style route). `/cart` has no page route today (it is a drawer); it is gated defensively. The gate
wraps the server component as `children`, so the button node is still rendered into static HTML on every allowed
route — `usePathname` resolves during SSR too, so this is **not** a hydration-only filter. No route group, no
per-route layouts, no duplicated `<Script>`.

Everything else is untouched: the same `publisher.js`, the same `afterInteractive` strategy, the same CSP in
`next.config.js`, the same `data-theme="light"`, and still **no** `data-lang` (browser language).
