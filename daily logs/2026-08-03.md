# Daily Log — 3 August 2026

## Email System Refactor — Direct Inline Sending (no queue, no cron)

### Problem
Vercel's Hobby plan allows only **2 cron jobs at a minimum frequency of once/day**, so the 1-minute
`/api/admin/email/process` drain (vercel.json) could never actually run at 1-min cadence and reliable
scheduled/queue-driven email delivery was impossible. The old design enqueued every form submission and
depended on a background drain (`after()` + cron + manual) to actually call Resend — if the drain never ran,
emails sat in the queue as `pending` forever.

### Solution — Direct Email Posting
Web-form emails are now sent **directly (inline)** during the `POST /api/email/submit` request. Delivery no
longer depends on any scheduler. The MongoDB `email_queue` collection was repurposed as a **send ledger** for
exactly-once dedupe + retry auditing.

### Other ideas to solve the scheduling problem (no Vercel cron needed)
1. **Direct inline send (adopted)** — the default; no scheduling needed for instant notifications.
2. **GitHub Actions cron** — free workflow (`schedule: '*/5 * * * *'`) calls `POST /api/admin/email/process?batch=10` with `Authorization: Bearer <CRON_SECRET>`; Vercel's 2-cron limit doesn't apply.
3. **Upstash QStash** — free-tier scheduled HTTP requests (down to per-second) hitting the same retry endpoint; purpose-built serverless cron replacement.
4. **External uptime/heartbeat monitors** (UptimeRobot, Cronitor, Google Cloud Scheduler free tier) pinging the retry endpoint periodically.
5. **Admin-panel manual retry** — `processEmailQueue()` stays behind the "Retry Failed Sends" button for one-off drains.

### Key properties preserved
- **Exactly-once:** `jobKey = requestId` unique-index claim → retried/duplicate POSTs can never fire a second email.
- **Recipient security:** recipients still resolve server-side only (destination-first opt-in map, then per-form-type, then `RESEND_INTERNAL_TO`); clients can never choose who receives emails.
- **No enquiry loss:** the submission is always saved to `form_submissions` before the send is attempted; a failed send stays in the ledger (`failed`, retryable) instead of vanishing.
- **Bounded memory:** sent/failed/dead ledger entries TTL-purge after 30 days.
