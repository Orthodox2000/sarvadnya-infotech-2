cards come from a new projected, `.limit(3)` `getRelatedNews()` helper — `content` stays in the
Mongo projection only because seeded docs have no stored `readingTime` and `enrichNews()`
derives it from the body; it is stripped from the returned objects. New `lib/api-cache.ts`
holds one CDN header value applied to 11 public read GET routes; `next.config.js` repeats the
allowlist as exact-path header rules **after** the global no-store rule (Next uses
last-match-wins). `/api/identify` now returns 204 before rate-limit/parse/DB work for ignored

## 22. Signature horizontal scrollbar in the received email

Owner: *"email signature i still get scroll bar for some reason , instigate"* — clarified
as a **horizontal bar at the bottom of the received email** (not when opening the file).

Investigated with headless Chrome at 280–1440 px, both the standalone file and the bare
first-table-to-last-table paste region: `scrollWidth === clientWidth` everywhere, zero
overflowing elements, zero elements with internal overflow, no blank tall rows, and still
zero overflow with forced wide fallback fonts (monospace, DejaVu Sans, Liberation Serif).
So the HTML has no browser-level overflow — the cause is in the wrapper's mail rendering.

- **Cause 1** — the outer `width="100%"` table had `padding:24px 12px` on its cell.
  Outlook's Word renderer adds cell padding to a 100%-width table, giving `100% + 24px`
  and a permanent horizontal scrollbar. Mail clients strip `<body>` styles, so the old
  `overflow-x:hidden` could never suppress it.
- **Cause 2** — `overflow-x:hidden` on `<body>` alone (after the `<style>` block was
  removed) forces `overflow-y:auto`, making the body a scroll container. Measured
  `hidden / auto`.

Fix in `email-templates/email-signature.html`: removed `overflow-x:hidden`; replaced the
padded cell with real 24px spacer rows above/below and a nested 100%-width table with 12px
gutter cells flanking the `width="600" align="left"` card. No percentage-width cell has
