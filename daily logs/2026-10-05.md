### Implementation — three grid areas, DOM order doing the work

The two requirements are in tension. "Aligned with the main title" needs the h1 inside the grid so area 2's top edge **is** the h1's top edge. "Login first on mobile" needs the auth area to come before the openings. Wrapping the whole thing in `order-*` would satisfy both visually and break the **tab/reading order** (WCAG 1.3.2 / 2.4.3) — worst on exactly the layout where sign-in is the primary control.

Resolved with **explicit grid placement and no `order` at all**. DOM order is `title → sign-in → openings` at every breakpoint:

| | stacked (<768) | md and up |
|---|---|---|
| area 1 heading | row 1 | col 1, row 1 |
| area 2 auth | row 2 | col 2, rows 1-2 → **top edge == h1 top edge** |
| area 3 openings | row 3 | col 1, row 2 |

## B. ENVIRONMENT — 7 orphaned dev servers (not a product defect)

A cold-start verification attempt failed with `HTTP 500` and hundreds of `ENOENT … build-manifest.json` errors. It was **not** the careers change and **not** a Next.js fault. Root cause, found by inspecting the listening sockets:

```
ss -ltnp → 7 listeners: 3000 3001 3002 3003 3004 3005 3006
```

**Seven `next dev` processes were alive simultaneously**, each from a `nohup npm run dev &` restart. My earlier `pkill -f 'next dev'` had never matched anything, because the running processes are named **`next-server (v15.5.19)`** and `node …/node_modules/.bin/next` — neither contains the string `next dev`. So every "restart" silently added a server instead of replacing one.

Three separate symptoms all traced back to that:

| Symptom | Real cause |
|---|---|
| `ENOENT … app-paths-manifest.json` | 7 Turbopack processes rewriting the **same** `.next` concurrently (AGENTS §9's documented dev/build corruption, arrived at from the dev side) |
| `/careers` returning 500 | the 500-serving orphan still owned **port 3000**; the new server silently moved to 3006 (`⚠ Port 3000 is in use…`) and `curl localhost:3000` kept hitting the broken one |
| `JSON.parse` "Unexpected token 'I'" / `null.toLowerCase()` | assertions ran against a half-compiled tree before the suite knew the server was up |

**Memory made it fatal.** Free RAM had fallen to **275 MB** (available 1390 MB) on the documented 7.5 GB box, so Turbopack workers were being starved mid-write. After the kill: 728 MB free / 2216 MB available.

### The NTFS-3G red herring

`rm -rf .next` failed with `Directory not empty` and left `.fuse_hidden*` tombstones, which looked like filesystem corruption. It was not: **FUSE creates a tombstone per unlinked-but-open file, and the 7 live servers held handles inside `.next`.** Once they were dead, `rm -rf .next` succeeded on the first try with no residue. This repo is on an `ntfs-3g` mount (`/mnt/EE26599E2659691B`), so undeletable `.next` content is a **symptom of a live process holding it**, not a broken disk — chase the process, not the filesystem.

### Two traps hit while cleaning up

- **`pkill -f` kills the invoking shell.** The pattern matches the agent's own `bash -c` command line, which contains the pattern. It reported `Killed by SIGTERM` with no other output. Two escapes: bracket one character (`next[-]server`) so the literal text in the command line cannot match its own regex — but this still failed when a *later* part of the same command line contained the plain string (`pgrep -af 'next-server…'`); and, finally, **collect numeric PIDs first, kill by number in a separate call**, since numbers cannot self-match.
- **A stray `nohup … & sleep 25; for i in $(seq …)` wrapper shell outlived its own job** and kept polling with `curl`, resurrecting servers. Background helpers need their PIDs recorded.

### Guardrails added

`/tmp/opencode/verify-careers.cjs` now polls `/api/careers/visible` until it returns **parseable JSON** (`waitForApiReady`, 180 s cap) and derives `EXPECTED` from that response, instead of the old one-line `(await (await fetch(…)).json()).length` which threw an alarming undici stack trace and reported "crash" before a single assertion ran. A warm-up navigation on `/careers` handles the second cold-start case where the API is up but Turbopack has not compiled the route.

### Rule to keep

**Verify one dev server, not zero.** Before any browser verification: `ss -ltn | grep -E ':30[0-9][0-9]'` must show **exactly one** listener. And to stop one safely, kill by PID from `ss -ltnp` — never `pkill -f 'next dev'`, which matches nothing that actually runs.

### Final environment state

Recovered and confirmed: **one** `next dev` on port 3000, `/careers` = 200, `/api/careers/visible` = 200, ready in 4.3 s, `.next` fully removed and rebuilt clean, repo root free of `.next*` junk, `git status` showing only the 17 intended careers/doc changes and no build artefacts. ## C. ROUND 4 — fixed 260px sidebar → a real 60/40 split

> Owner: *"i dont want such a long sign in spanning entire width, signing using just 40% space on right and emaining 60% space wdith bu open positing on same for md and above"*

One-line change — `md:grid-cols-[minmax(0,1fr)_260px]` → **`md:grid-cols-[minmax(0,3fr)_minmax(0,2fr)]`** — but it invalidates round 3's central claim, so the reasoning is recorded.

### The fixed width was only ever "40%" at one viewport

Round 3 shipped a **constant 260px** sidebar and called the hierarchy solved. That was wrong in the way that matters: a fixed pixel column is a fixed *share* only by accident, and only at the width you measured it at.

| viewport | sign-in px | sign-in as a **share** | openings as a share |
|---|--:|--:|--:|
| 768 | 275 | 40% ✓ | 60% |
| 1024 | 378 | 38% | 62% |
| 1280+ | 260 (round 3) | **23%** ✗ | **77%** |

So at desktop the owner was being handed a 23% sidebar while being told it was balanced — the share was drifting the whole way, in the direction away from the request. A ratio holds **60/40 at every `md`+ width by definition**, which is the actual requirement. Measured after: ratio **1.50 at all eight md+ widths** (768 → 1920), no drift.

It also removes a whole class of bug structurally. Round 3's `320 → 360px` step at `xl` had made the main column *narrower* on a *wider* window; `fr` units cannot express that, since both tracks scale with the container together. Openings now measure 413 → 444 → 492 → 566 → 660 → 672px, monotonic.

### `minmax(0, …)` on both tracks, not bare `3fr 2fr`

Grid items default to `min-width: auto`, so one long unbroken string in the openings list can push its track past its share and overflow the page — the same failure class that made the desktop navbar row paint under the search bar. `minmax(0, …)` lets a track shrink below its content's min-content width.

| viewport | openings | sign-in | ratio |
|---|--:|--:|--:|
| 360 / 640 | stacked, full-bleed | stacked | — |
| 768 | 413 | 275 | 1.50 |
| 1024 | 566 | 378 | 1.50 |
| 1280+ | **672** | **448** | 1.50 |

Note the desktop openings column is **narrower than before** (672 vs 860). That is the request, not a regression: 60% of a container capped at 1152px *is* 672px, and the space went to the sign-in, which is where it was wanted. Below `md` the grid stays single-column — at 360px a 40% track is 131px, which cannot hold an email input, so "for md and above" is the right boundary.

### The sign-in finally has room

The 260px column was cramped: the password field's 44px reveal gutter left ~173px of text space and the "Create account" expander was squeezed. At 448px the password field has 346px. A card-internals probe confirms **no control overflows the card's padding box at 275 / 378 / 448px**, and all controls now measure 36–44px tall.

### Accessibility fix found while measuring: a 17px tap target

Probing the card's controls surfaced a control at **17px tall** — the "Create account" mode toggle, a real control that swaps the entire form, not decorative text. That is below the 24×24 CSS px floor of **WCAG 2.2 SC 2.5.8 (Target Size, Minimum)**. Pre-existing (it was 17px at 260px too), but it was invisible until something measured it. Fixed with `inline-flex min-h-9` → **36×95px**: the box is a real target while the label still renders as an inline text link, and the negative margin keeps it aligned with the sentence beside it.

### A test that had been asserting something false

`auth column stays on screen after scrolling` failed after this change. It scrolled to `y=600` and demanded the card still be fully visible — but **the page only has 348px of scroll in total**, and `scrollTo` silently clamps. The narrower openings column wraps rows less, the document got shorter, and the assertion was being made against a scroll position that does not exist. The sticky is not broken: with 2 openings the grid area is barely taller than the 375px card, so it correctly has nothing to pin against.

Split into two checks that assert what is actually guaranteed:

1. **`sign-in card still reachable at maximum scroll`** — scrolls to the clamp, asserts the card is still on screen. Always true.
2. **`sign-in card pins at md:top-28 (112px) once the openings list is long enough`** — injects rows *in the browser only*, then asserts the pin at exactly 112px. This is the stronger check and it *proves* the sticky rather than assuming it. Rows are undone by a reload before later assertions, so nothing downstream measures a doctored page.

The lesson is the one worth keeping: **that old assertion was passing for the wrong reason.** It had been satisfied incidentally, and a layout change nobody had reason to distrust turned it red.

## D. ROUND 5 — `md` (768px) → `sm` (640px): the split was behind a width nobody was hitting

> Owner: *"whichever size i see, i see signin on top and opening at nottom, and not left rifght"*

This was **not** a layout bug. Proved before touching anything.

### Step 1 — verify the CSS was actually being served

The claim "the split never applies" is a claim about the stylesheet, so the stylesheet got checked first:

```
.md\:grid-cols-\[minmax\(0\,3fr\)_minmax\(0\,2fr\)\] {
  grid-template-columns: minmax(0, 3fr) minmax(0, 2fr);
}
```

emitted correctly — inside **`@media (min-width: 48rem)`**. 48rem = **768px**. So the rule was correct, scoped exactly as written, and simply did not apply below 768px. The sub-768 stacked layout was the designed behaviour, not a failure.

### Step 2 — my own probe printed the layout label BACKWARDS

The first sweep reported `360 | side-by-side | 328 | 328 | 50%`. Both columns 328px wide cannot be side by side in a 360px viewport — they are stacked, full-bleed. The variable was named `stacked` but assigned the **side-by-side** test:

```js
stacked: ar.left >= or.right - 2,   // this IS the side-by-side test
```

The numbers were correct throughout; the printed word was inverted. Corrected to:

```js
sideBySide: ar.left >= or.right - 2, // auth block sits beside the openings
```

Worth recording because a probe that lies about the direction of a layout is worse than no probe — it would have "confirmed" the owner's complaint for the wrong reason and sent the fix in the wrong direction.

### Step 3 — the clue that mattered

Corrected sweep:

| width | layout |
|---|---|
| 360 – 767 | **STACKED** (sign-in above openings) |
| 768 + | side-by-side, sign-in exactly 40% |

Owner was asked where they were viewing, and answered **a desktop or wide monitor**. That is the diagnostic detail, because it makes 768px implausible as the explanation: the CSS is correct, so their *CSS viewport* was under 768px. All three of these shrink it invisibly on a large screen:

### Two bugs in my OWN test suite, caught before they became a false alarm

The rebuilt suite first reported **29/30**. Both failures were test defects, not product defects, and both are the kind that would have burned a future session:

**1. `password reveal works` — clicked and read the DOM in the same synchronous `evaluate`.**

```js
btn.click();
return document.querySelector('input[type="text"][id="careers-password"]') !== null;
```

React 19 had not re-rendered by the time the next line ran, so `type` was still `"password"` and a **working** toggle reported as broken. The markup was correct (`<div className="relative">` holds both the input and the button, so the selector was fine). Fixed by splitting click and settle, and while in there added the accessibility assertion the eye toggle should have had all along:

```js
btn.click();
await new Promise((r) => setTimeout(r, 400)); // let React commit the state flip
```

plus `aria-pressed === 'true'` **and** `aria-label === 'Hide password'` after the toggle.

**2. `openings + login both present at every width` — a race, and it flipped between runs on identical code.**

It passed on run 1 and failed on run 2 with no source change in between. The geometry loop's readiness gate was only:

```js
document.querySelectorAll('article').length > 0   // openings rendered…
```

…but the auth column renders a **skeleton** (`aria-busy="true"`) until `/api/auth/careers/me` resolves. Measuring inside that window found no `#careers-email`, and the check read as a layout regression that did not exist. The product was fine — `careers-client.tsx:205` deliberately renders a pulse skeleton, not a blocking "Loading…", so the openings beside it stay live and there is no empty-box flash. The **gate** was wrong:

```js
document.querySelectorAll('article').length > 0 && !document.querySelector('[aria-busy="true"]')
```

Stability was then proved rather than assumed: **run 1 and run 2 both 31/31**.

The general rule: a check that flips between runs on unchanged code is a *flaky* check, and the correct response is to find the race, not to re-run until green. Re-running to get a pass is how a real regression gets shipped.

### Environment note — two things the restart broke

Worth writing down, because both look like product bugs and neither is:

1. **The dev server died mid-question** and was restarted (one listener confirmed before any browser verification).
2. **`/tmp/opencode` was wiped**, taking every probe script with it — `verify-careers.cjs`, `measure-cols.cjs`, `probe-auth-card.cjs`, the bisect/debug scripts. The suite was rebuilt from scratch as one consolidated `verify-careers.cjs` covering geometry + both auth states + runtime health, and re-run until deterministic. Probe scripts are throwaway by design, but the *lessons* they encode are not, and the rebuilt suite re-encodes every one of them in its header comment: `headless: 'shell'` (full `chrome` segfaults, exit 139) · case-insensitive text matching (`text-transform: uppercase` makes `innerText` return `"APPLY NOW"`) · expected row count read from the API, never hardcoded · signed-in state proven by **browser-only** interception of `/api/auth/careers/me` + `/logout`, never a real login (the login and session writes are *not* `isIgnoredRequest`-gated, so a real attempt would write to the live production database) · API readiness polling, because a cold `next dev` answers with the plain text `"Internal Server Error"` and an unguarded `.json()` throws deep inside undici · `document.body.style.overflow === 'hidden'` as the modal-open signal, **not** `input[type=file]` (the signed-in `ResumeManager` renders one too).
3. **Git began refusing every command** with `fatal: detected dubious ownership`. Cause: the repo tree is owned by `root:root` (uid 0) while the shell runs as `sarvadnya` (uid 1000) — an artifact of the restart, not a permissions fault in the repo. Fixed with the documented `git config --global --add safe.directory` for the frontend repo and the nested one. No `.git/config` in either repository was modified.
