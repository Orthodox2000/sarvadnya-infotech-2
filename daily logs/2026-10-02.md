## ⛔ Finding 1 — the 137 "modified files" contained ZERO real work

Before moving, the nested repo showed **137 modified files**. That looked like three months
of unsaved admin work. It was not.

```
git diff HEAD~1 HEAD --shortstat                  → 137 files, 32353 insertions(+), 32353 deletions(-)
git diff HEAD~1 HEAD --shortstat --ignore-all-space → (empty)
```

**Every one of the 137 files was LF in git and CRLF on disk.** `git add -A` normalised
LF→CRLF across the whole tree. Zero substantive changes. The equal insert/delete counts were
the tell.

Root cause: `core.autocrlf` unset, `core.eol` unset, and **no `.gitattributes`** in the
nested repo — so the drift went unnoticed. This is the same CRLF-noise class already flagged
in this repo on 2026-10-01.

**Consequence:** the checkpoint commit is a pure line-ending rewrite. It must **not** be
pushed as if it were work — it would present as a 32k-line diff. It was kept only because it
gives the move a named rollback point and leaves the tree clean.

## ⛔ Finding 2 — `tsc` swallowed the nested repo, and the failure mode was *silent corruption*

`tsconfig.json` has `"include": ["**/*.ts", "**/*.tsx"]` — recursive from this repo's root —
and `exclude: ["node_modules", "cpanel-landing"]`. `npm run typecheck` is `tsc --noEmit`.

Measured **after the move but before the fix**, to prove the hazard was real rather than
theoretical:

| Metric | RED (no `exclude`) | GREEN (with `exclude`) |
| :-- | --: | --: |
| Files in `tsc` program | **1003** | **836** |
| Files from the nested repo | **167** | **0** |
| `error TS` reported | **10** (10/10 foreign, 0 in this repo) | **0** |

(1003 − 167 = 836 — the program shrank by exactly the nested tree.)

The error count was the *least* important number. The real problem is
`compilerOptions.paths`:

```jsonc
"paths": { "@/*": ["./*"] }
```

`./*` is relative to **this** repo's root. So when a nested admin route writes
`import { x } from '@/lib/admin-auth'`, TypeScript resolves `@/` against **this** repo —
where `lib/admin-auth.ts` **does not exist**, because it was deliberately deleted along with
the admin panel. Observed:

```
sarvadnya-advanced/app/api/admin/login/route.ts(2,68):
  error TS2307: Cannot find module '@/lib/admin-auth'

sarvadnya-advanced/app/admin/email-config/page.tsx(4,53):
  error TS2305: Module '"@/lib/form-destinations"' has no exported member 'KNOWN_DESTINATION_KEYS'
```

**That second error is a trap with a plausible wrong fix.** The obvious way to silence it is
to **add `KNOWN_DESTINATION_KEYS` to this repo's `lib/form-destinations.ts`** — which would
corrupt the **public frontend's live `EMAIL_DESTINATION_RECIPIENTS` routing**, in a repo that
does not own that dependency, purely to satisfy an admin build. The `exclude` entry is the
prevention; without it the failure invites exactly that regression.

Note the existing `cpanel-landing` entry in `exclude` — **the identical problem, already
solved here on 2026-08-05.** There is an established precedent to follow, and it was
followed.

## ⛔ The design decisions that are load-bearing

- **Embedded `statusHistory[]`, not a separate collection.** The Atlas cluster may be **M0**,
  which does **not** support multi-document transactions — a separate collection means two
  writes and status/history can disagree. One document, one atomic update.
- **Events store `to` only; `from` is derived** by walking the timeline backwards. Storing
  `from` would force a read-before-write to learn the current status, opening a race between two
  admins acting simultaneously.
- **No backfill.** Existing renewals predate the feature and their true history is unrecoverable.
  A synthetic prior state would be fabrication and would be indistinguishable from real history
  afterwards. Oldest entry renders `from: null` → "created as", plus a "History began 2026-10-02"
  footnote.
- **`actor` is always the constant `'admin'`.** `lib/admin-auth.ts` hardcodes one identity and
  the session token carries **no username**, so attribution is structurally impossible today. The
  trail's value is the timeline, not who did it.

## ⛔ Three SDK facts that would have shipped as bugs

**1. `validatePaymentVerification` takes the WRONG parameter names.** It reads
`params.order_id` / `params.payment_id` — Razorpay's callback field names — not the
`razorpay_order_id` / `razorpay_payment_id` our checkout actually receives. Passing the raw
payload throws. I verified this behaviourally across 7 cases rather than trusting the types.

**2. The SDK compares signatures with `===`, not constant-time** (`razorpay-utils.js:72`). So we
verify with our own HMAC and `crypto.timingSafeEqual`, and still use the SDK for order
create/fetch. Accepts either hex casing, because Razorpay's casing must not be load-bearing.

**3. `payment_capture` is typed `boolean`, not the `1`/`0` the REST docs show.** Passing `0` both
failed typecheck and broke overload resolution, which is why the error read
`Promise<RazorpayOrder> & void` — TypeScript could not choose between the promise- and
callback-returning overloads. Fixed by **omitting** the field: the Orders API defaults to no
auto-capture, which is what we want anyway. Relatedly, `RazorpayOrder.amount` is `number | string`
because the response type inherits the looser *request* body; that figure goes straight into the
browser's Checkout call, so it is now **validated**, not cast.

## Two real bugs the E2E suite caught (both fixed)

1. **React 19 Strict Mode double-counted bundle companions.** Dev Strict Mode double-invokes `setItems` updaters to surface impurity; the old `addBundle` did `addedCompanions.push(...)` *inside* the updater, so the popover copy said "+ 4 paired items" for a 2-companion bundle (items were still correct — the updater is pure). Fixed by **computing** the additions inside the updater and **assigning** (never mutating) an outer variable — both invocations compute the identical list, the second write overwrites the first with the same value. `lib/cart/store.tsx`.
2. **Cart drawer was zero-size on phones.** The only `<CartDrawer />` mount lived inside the navbar's desktop variant, which sits in a `hidden lg:flex` container — at <1024px that ancestor is `display:none`, and *no descendant (fixed or not) renders inside a display:none box*, so an open drawer measured 0×0 at 360px and 1440 only worked by luck. Fixed by mounting the drawer **once in `app/(site)/layout.tsx`**, a sibling of the sticky chrome; both navbar variants are now pure triggers. Verified: probe at 360 shows drawer width = 360.
