## Session: GSC structured-data cleanup + a line-by-line factual audit of every news post and every Tally Insights lesson

Owner brief (condensed): Google Search Console reported **structured-data issues on
`/products/tallydrive`, `/services/tss` and `/products/silver`** - fix them. In the same pass the
**content must be 100% factual and correct**: no invented facts, no guessed menu paths, nothing that
can be contradicted by Tally's own documentation. Audit scope was set to the **widest** option - all
news posts and all 16 Tally Insights lessons, not just the three flagged pages.

Two standing constraints shaped the work:

- **The return policy is never published.** Licences are returnable in limited cases, with no time
  limit and no cooling-off window - but that policy is internal knowledge only and must not appear on
  the frontend or in an email to a customer.
- **No invented facts to satisfy a validator.** A Search Console "missing field" note is not
  permission to make something up.

Everything below was produced by reading the actual code/seed, not by assumption, and every content
claim was checked against Tally's own documentation before it was written.

### §6 - New guard: `scripts/schema-audit.mjs`

### §13 - The one rating that survives: `lib/rating-summary.mjs`

New pure-ESM, zero-dependency module (plus a hand-written `.d.mts`, the same pattern as
`lib/email-autoreply.mjs` / `lib/careers-referral.mjs` / `lib/sara-guard.mjs`):

- `normalizeRating(value)` - accepts a number **or** a numeric string (a DB import or admin edit can
  leave `"5"`), returns `null` for anything outside 1-5. `null` is a real state: an imported Google
  review may carry no stars, and inventing one would be fake social proof.
- `summariseRatings(reviews)` - `{ average, count }` from the reviews that actually have a rating, or
  **`null` when nothing is rateable**. Callers must render nothing in that case, never a default.
- `formatRating(summary)` - one decimal (`"4.5"`), null in / null out.

`app/components/CustomerReviews.tsx` is now the **only** place a rating appears, and it computes it:

- header average from `summariseRatings(reviews)` where `reviews` is the same list the wall renders
  (fetched from `/api/reviews`, falling back to `staticReviews`), so adding, editing or deleting a
  review moves the number **by itself** and the "from N reviews" count can never exceed the cards shown;
- `aria-label="4.5 out of 5 stars from 4 reviews"` so the number is machine-readable;
- `StarRating` now renders a **partial** star (two stacked rows, gold clipped to `average / 5`), because
  a computed average lands on values like 4.5 and rounding up would overstate the reviews;
- cards use the same `normalizeRating()` gate as the average, so a card can never show stars the
  average ignores.

Measured live after the change: `/api/reviews` returns **4** reviews, all with ratings, average **4.5**,
and the homepage prints exactly `4.5` / "from 4 reviews".

### §14 - Guards so the fakes cannot come back

`scripts/schema-audit.mjs` was rewritten around the new rule (still dependency-free, still the third
entry in `test:all`):

1. `aggregateRating` may appear **nowhere** in `app/` or `lib/`.
2. No hand-typed star figure anywhere - the rule is `\b(rating|reviews)\s*:\s*['"\`]\d`, so TS
   annotations (`rating: number`) and log strings stay legal while `rating: '4.8'` fails.
3. The permitted path must **exist and actually be used**: `lib/rating-summary.mjs` must export the
   three helpers and `CustomerReviews.tsx` must import it and call `summariseRatings()` - otherwise
   rule 1 would pass simply because nothing displays a rating at all.

New `scripts/rating-summary-test.mjs` (**18 assertions**, `npm run test:ratings`, last entry in
`test:all`): invalid/edge inputs, numeric strings, out-of-range rejection, the "nothing rateable ->
null" contract, one-decimal rounding, and that a mixed list ignores unrated reviews instead of
treating them as zero.

## Session 5 - Visitor analytics: the count sat below Search Console, and bots were listed as people

**Owner:** *"AI/bot seperation r visitor list [is wrong]"*, raised while comparing the panel against GSC.

Three independent defects, all measured against the live collection (1,328 session documents):

### §15 - Crawlers were stored as humans (write side)

`parseDevice()` in `lib/visitors.ts` only knew `bot|spider|crawler|slurp|curl|wget|headless|puppeteer|
phantom|preview`. Live evidence: **16** docs of `facebookexternalhit/1.1` (Meta's link-preview
fetcher), **2** of `Google-NotebookLM` and **2** of `(compatible; Dataprovider.com)` were stored as
`device.type: 'unknown'` and therefore counted as people - one of them occupied **17 sessions**.

`BOT_UA_PATTERN` is now an **exported string**, grouped so a future reader knows why each token is there:
classic crawlers · link unfurlers / social previewers · AI / answer-engine crawlers (`chatgpt`, `openai`,
`gptbot`, `oai-searchbot`, `claude`, `anthropic`, `perplexity`, `cohere`, `ccbot`, `bytespider`,
`notebooklm`, `googleother`, `google-extended`, `mediapartners`) · SEO / monitoring / security scanners
(`ahrefs`, `semrush`, `mj12`, `dotbot`, `dataprovider`, `bitsight`, `pagespeed`, `lighthouse`, `uptime`,
`pingdom`, `censys`, `shodan`, `nmap` ...) · headless renderers · plain HTTP clients (`curl`, `wget`,
`okhttp`, `python-requests`, `axios`, `node-fetch`, `undici`, `java/` ...).

**Deliberately excluded: bare `whatsapp`, `telegram`, `linkedin`, `twitter`, `pinterest`, `discord`.**
Those words also appear in **in-app browsers used by real customers** - a WhatsApp or LinkedIn in-app
tap would have been counted as a bot, and WhatsApp traffic in India is large. Each of those products'
*crawler* is already caught by the `bot` token (`LinkedInBot`, `Twitterbot`, `Pinterestbot`,
`TelegramBot`).

### §16 - Historical rows reclassify at READ time (no migration)

The write-side fix only helps from the next deploy onward, and the collection already held thousands of
misclassified rows. The nested admin's `lib/visitor-groups.ts` therefore carries the **same pattern**
as a Mongo regex and reclassifies on every read:

- `BOT_UA_PATTERN` + `BOT_UA_MONGO = { $regex, $options: 'i' }`;
- `HUMAN_MATCH = { 'device.type': { $ne: 'bot' }, userAgent: { $not: BOT_UA_MONGO } }` (spreadable;
  a **missing** `userAgent` passes `$not`, so a real visitor can never be hidden by an absent field);
- `BOT_MATCH = { $or: [{ 'device.type': 'bot' }, { userAgent: BOT_UA_MONGO }] }` - **not spreadable**.

`app/api/admin/visitors/route.ts` was rebuilt to build `$and` clauses instead of one spread object.
This is the bug that would have shipped silently: `BOT_MATCH` is now a top-level `$or` and the `q`
search also needs a top-level `$or`, and two `$or` keys cannot coexist - assigning one **replaced** the
other, so a search in the Bots tab would have listed humans and a device filter would have re-admitted
every bot.

The two repos cannot import from each other, so the duplication is deliberate; group **8** of the nested
suite asserts the two strings are **byte-identical** (674 chars).

### §17 - The "Visitors Last 24 Hours" KPI measured the wrong field

The card windows on `firstSeen`, but a `visitors` document is **one session keyed by the 1-year
`svd_vid` cookie** - so a returning visitor carries a months-old `firstSeen` and dropped out of the card
entirely. Measured: **5** unique humans with `firstSeen >= 24h` vs **8** with `lastSeen >= 24h`, and the
Visitors screen (which already used `lastSeen` for `activeToday`) said 8. Now `lastSeen`, so the two
agree.

### §18 - Hidden-tab page views were being discarded

`VisitorProvider.send()` returned early when `document.visibilityState !== 'visible'`, and the path was
**thrown away** - so someone who opened a Google result in a background tab (mobile especially) was
never recorded. The path is now parked in `pendingPathRef` and flushed by a `visibilitychange` listener
the moment the tab becomes visible. The beacon is still **not** sent while hidden (that rule was
correct), it is simply no longer lost.
