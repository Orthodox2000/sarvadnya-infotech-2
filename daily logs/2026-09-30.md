## ✅ COMPLETED — `app/components/ConsentBanner.tsx` (NEW, 93 lines) — **v1, superseded twice, see below**

A small, purely **informational** notice pinned bottom-left, deliberately **not** a consent gate.

- **No accept/decline gate.** Nothing is blocked until the visitor acts; consent is assumed by browsing. This keeps the component out of the critical rendering path and avoids an interstitial that would tank the bounce rate on a lead-generation site.

- **Storage-failure tolerant.** A `try/catch` around both read and write means private mode / disabled cookies still shows the notice (it just cannot be remembered) — a repeat view is preferable to a silent omission.
- `React.memo` wrapped export (matches the `Productbar` / `CustomerReviews` / `FAQ` memoization convention).
- **Copy:** "We keep a few records as you browse — your IP, device, and pages read. Browsing counts as consent. *view more*". ### 🐛 Real bug caught only because the harness used a genuine touch profile

A touch tap does not fire mouse events on its own. The browser synthesises them right after `touchend`, in this order:

```
pointerdown → touchstart → touchend → mouseover → mouseenter → mousedown → click
```

A naive `onClick={() => (open ? close() : open())}` therefore reads `open === true` (the synthetic `mouseenter` has *just* set it) and immediately shuts the card again. Instrumenting the pill proved it: the tap fired a **genuine `click`** on the button and the card **still never appeared**. **The feature was 100% broken on phones — the main audience.**

Fixed by snapshotting intent in `onPointerDown` (the one event that reliably precedes the synthetic mouse burst) and toggling off that ref rather than off the `open` state:

```js
const openBeforeBurst = useRef(false);
onPointerDown={() => { openBeforeBurst.current = openRef.current; }}
```

The snapshot reads an `openRef` mirror rather than the `open` in its render closure, because a mouse click arrives as mousemove → mousedown in quick succession and the closure still held the pre-hover `false`.

A **second, related** bug: a touch never fires `mouseleave`, so the 5-second countdown was never armed on a phone and the card sat open until the next navigation. The click handler now starts the timer itself when it opens the card.

So the final behaviour matrix is: **mouse** — hover opens, click shuts, leaving collapses after 5s. **Touch** — tap opens, tap again shuts, auto-collapses 5s after the opening tap. **Keyboard** — focus opens, Tab reaches Learn more and the X, blur collapses after 5s.

# THREAD A — HP LaserJet 1020/1080 Plus USB printer (Ubuntu)

Hardware: HP LaserJet 1020 (reported as `1080 Plus`), USB `03f0:2b17`, serial `JL32RQZ`. This consumed the bulk of the day.

## The problem, in order

1. **Display resolution** — attempted custom `xrandr` modes (`1336x768_60.00`, then `1336x768R` with reduced-reduced blanking via `cvt -r`). Landed on a working mode, then traced the underlying cause: **`nomodeset` was present in `GRUB_CMDLINE_LINUX`**. Backed up `/etc/default/grub` to `grub.bak.<timestamp>`, stripped the flag, ran `update-grub`, verified `nomodeset` count = 0 in the generated `/boot/grub/grub.cfg`, then rebooted.
2. **Driver install** — the HPLIP `hp-plugin` download was dead (the `hplip.sf.net/plugin.conf` host and the plugin's own URL were unreachable). Installed `printer-driver-foo2zjs` + `printer-driver-foo2zjs-common` instead, and separately downloaded the real plugin `hplip-3.24.4-plugin.run` from `openprinting.org`, **SHA1-verified it** (`c41c8380cac5db321659df341bf2ffc6315d9c20`), and installed it headless with `--keep --nox11`.
3. **Prints hung.** Jobs reached CUPS and then sat in the queue forever. `hp-probe` also hung indefinitely (had to be wrapped in `timeout`).

## The debugging that actually solved it

- **Log level raised to `debug`** in `/etc/cups/cupsd.conf` (reverted to `warn` afterwards), then job-by-job read out of `/var/log/cups/error_log` and the `/var/spool/cups/c00007` job-control files.
- **`usbmon` capture** — `modprobe usbmon`, then `cat /sys/kernel/debug/usb/usbmon/1u` for 12–25s windows while a job ran. Custom Python parsers (`dump.py`, `decode.py`) filtered on `Bo:1:002` and the ` S ` (submission) events to reconstruct the **exact byte stream being sent to the printer**.
- **Root cause #1 — the kernel `usblp` driver was claiming the printer interface.** It binds the printer USB interface as a raw device, which starves HPLIP of the endpoint it needs. Checked `85-hplj10xx.rules`, `udevadm info -a`, and the `usblp` uevent.
- **Root cause #2 — TWO cupsd daemons were running.** A **snap CUPS** (`snap.cups.cupsd`, socket at `/var/snap/cups/common/run/cups.sock`) and the **system CUPS** (`/etc/cups/cupsd.conf`, port 631) were both accepting jobs. `lpstat` was talking to one server while the job spooled through the other, which is why queue state looked contradictory. `systemctl stop snap.cups.cupsd` resolved the split-brain.
- **USB re-enumeration attempts** — deauthorize/authorize, then full unbind/bind of device `1-9` on `/sys/bus/usb/drivers/usb/{unbind,bind}`.
- **`strace` on the CUPS HP backend** (`/usr/lib/cups/backend/hp`) tracing `write,writev,ioctl,openat`, installed as a wrapper script. The real backend was backed up to `/tmp/opencode/hp.real` and **restored + md5-verified** afterwards. Also found the backend was hanging on the print pipe and holding `/dev/bus/usb/001/002`.
- **Byte-level PJL comparison.** Extracted the genuine Windows driver with `7z` from `~/Downloads/hp_LJ1020_Full_Solution-v2012_918_1_57980.exe`, read `HPLJ1020.INF` for the USB IDs, then ran `strings` on `hp1020.img` to extract the driver's real `@PJL` command list. Decoded our captured stream to compare — the difference was in the `USTATUS DEVICE =` form (ours had a stray **space before the `=`**) and the `ENTER LANGUAGE` variants.
- **A wrong udev rule was written and then removed.** `99-hp1020-no-usblp.rules` used two **invented env vars** (`USB_IGNORE_HPLIP_USBLP` / `USBLP_IGNORE_IF_PRODUCT`) that HPLIP never reads. HPLIP detaches the kernel driver itself at runtime, so the rule was pointless — deleted, and the reasoning recorded in the shell history.

- Installed `avahi-utils`; confirmed the queue is advertised with `avahi-browse -rt _ipp._tcp` and resolves as `HP-LJ1080._ipp._tcp.local.`
- **Final proof:** a test page submitted to the **LAN address** `lp -h 192.168.1.35:631 -d HP-LJ1080` completed and cleared the queue, and a plain local `lp -d` print also succeeded.
- Firewall checked (`ufw status`, `nftables`, `firewalld`) — none blocking.

# THREAD B — LAN SMB / NetBIOS browse-list discovery

Goal: enumerate the office LAN's Windows/SMB hosts from Linux.

- `nmblookup` against the neighbour set, plus `__MSBROWSE__` node-status and `S -U 192.168.1.7` browse-list queries against the apparent master browser.
- **`tcpdump` capture of UDP 137/138** → `browse.pcap`; decoded with `tcpdump -X` and a custom `decode.py`; several follow-up parsers (`msbrowse.py`, `browselist.py`, `getbrowse.py`, `nbstat2.py`, `nbtest.py`, `bcast.py`).
- `validate.py` / `sweep.py` — full `/24` sweep, then a targeted port probe (135/139/3389/5985/22/631/80) across the live IPs.
- **SSDP** — captured UDP 1900 → `ssdp.pcap`, plus a hand-rolled `M-SEARCH` broadcast in Python and `ssdp.py`. Also `avahi-resolve-address` for mDNS reverse lookups.
- `smbclient -L //HOST -N -m SMB2` and a forced-SMB1 client config (`/tmp/opencode/client.conf`) tried against every discovered NetBIOS name (`SI-3A`, `SI-2`, `SUMANDELLLAP`, `SI-CSE1`, `SI-CSE5`, `SI-ACC1`, `DESKTOP-C7A61PP`, `SADDAM_SUPPORT`).
- Installed `smbclient` and `samba-common-bin` (both were missing).

**Conclusion (negative result, documented):** guest/anonymous browsing is not obtainable from these hosts. Anonymous `srvinfo` requires **SMB1/NT1 dialect**, which the modern machines refuse. Separately, a non-root process **cannot bind UDP 137/138** (`/proc/sys/net/ipv4/ip_unprivileged_port_start` is 1024), so `nmbd`'s browse-list participation and the broadcasts must run as root — `sudo -S -k` with a cached credential was required. The neighbours on this LAN are therefore discoverable only by IP, not by NetBIOS browse.
