### §5 — ⚠️ `shadcn` must stay in `dependencies` (do not "fix" this)

`app/globals.css` line 3 is `@import "shadcn/tailwind.css"`. A production install (`npm ci
--omit=dev`) would **fail the CSS import** if `shadcn` were moved to `devDependencies` — this exact
regression is recorded in the 2026-08-27 notes. It is therefore intentionally left in
`dependencies` even though it looks like a build-time tool.

### §6 — Audit posture (accepted, build-time-only)

`npm audit` reports **7 high** advisories, **all inside `shadcn@4.22.1`'s own dependency tree**
(CLI tooling, never shipped to a visitor). `npm audit fix --force` would **downgrade `shadcn` 4 → 1**
and break the CSS import above; every other package is already at its latest published version. The
`braces` advisory range is `*` (no fixed version exists). Net: **no runtime exposure, no safe fix
available** — accepted and recorded rather than forced.

## Session (2): Tally Insights artwork — the images that never rendered, and step 4 on the card border

Owner brief (verbatim, three messages): *"how to create a company image is underflowed and step 4

Two **independent** defects were behind those reports. Both were found by measurement, not by eye.

### §11 — Defect 1: five SVGs were malformed XML, so browsers refused to decode them

`tally-gst`, `tally-inventory`, `tally-career`, `tally-payroll` and `tally-reports` contained a **raw
`&`** in their text ("F11 > Statutory & Taxation > GST Yes", "Godowns & Batches", "BOM & Reports",
"Pay Heads & Structures", "Daybook & Registers", "Interview Q&A, ..."). A bare `&` is invalid XML,
and a browser will not render a malformed SVG **at all** — `<img>` stays blank.

The trap: the file is served perfectly. `curl -I https://sarvadnyainfotech.com/images/insights/tally-gst.svg`
returns **200 `image/svg+xml`**, so every HTTP/status check passes while the picture is empty. Only a
browser decode (`img.naturalWidth > 0`) proves it.

Fix: escape the bare `&` (`&amp;`) in the 5 files. All 15 SVGs now parse (`xml.etree`).

### §12 — Defect 2: step 4 sat exactly ON the card's bottom border

The shared 4-step template — card `1080x360` at `translate(60,200)` with rows at `cy` 80/160/240/320,
step title `cy+10`, detail `cy+40` — put the **last detail baseline at y=360**, i.e. the card's own
bottom edge. Measured text bottom = card bottom **+4px** → the last line crossed the border and read
as "cropped"/"underflowed". 11 files shared it.

Fixed by re-fitting the geometry (not by restyling):

| | Before | After |
| :--- | :--- | :--- |
| Card | `1080x360` (y 200–560) | **`1080x390`** (y 200–590) |
| Row `cy` | 80 / 160 / 240 / 320 | **71 / 147 / 223 / 299** (76px rhythm) |
| Card padding (top / bottom) | 61px / **−4px** | **47px / 47px** |
| Canvas margin (above / below card) | 40px / 70px | **40px / 40px** |

`latest-tally-prime` (3 rows, already safe) only grew to the same 390px card so every Insight card
now shares one height: 66px top / 76px bottom padding.

`erp9-vs-prime` had a related nit: the centred **"VS"** label at 42px was 45px wide in a 40px gap
between the two comparison cards, so its box overlapped both borders by ~2.5px → **32px**, `y` 370→378.

Measured card padding after the refit (browser `getBBox` + `getCTM`, 207 text boxes):

| file | card | top pad | bottom pad |
| :--- | :--- | --: | --: |

### §14 — New permanent guard

`scripts/insights-svg-audit.mjs` (`npm run check:insights-svg`, 3rd entry in `test:all`) is
dependency-free and catches exactly the two failure modes that shipped:

1. **XML well-formedness** — bare `&`, bare `<` inside text.
2. **Canvas/viewBox agreement** — a mismatched `viewBox` is what distorts or crops an image scaled by CSS.
3. **Card fitting** — inside any card group, no text may sit within 20px of the card's bottom edge or
   above its top edge, and the card itself must stay inside the canvas.

Text *width* fitting needs a font engine, so that stays with the browser probe; the guard locks the
two defects the owner actually hit.
