# Daily Log — 21 August 2026

## Zoho SalesIQ Tracking-Only Embed, New /addons Route, ProductBar Modules Split & Build Stability Fix

### 1. Zoho SalesIQ — Diagnosis, Removal of Chat UI, Tracking-Only Final State
The client-provided SalesIQ widget was not loading at all. Root cause found and then iterated
through 3 requirement changes in one session (fix → remove → tracking-only):

- **Root cause (why it never worked):** `next.config.js` Content-Security-Policy had **no Zoho
  domains anywhere** — `script-src` blocked `https://salesiq.zohopublic.in/widget?wc=...`,
  `connect-src` blocked its analytics beacons/websockets, `frame-src` blocked the chat iframe.
  The browser silently refused every SalesIQ request.
- **Embed method fixed:** the old setup used two separate `next/script strategy="afterInteractive"`
  blocks whose execution order was not guaranteed (init must run before the widget loader).
  Replaced with the client's exact snippet as raw SSR'd `<script>` tags at the end of `<body>` in
  `app/layout.tsx` — inline `$zoho` init first, deferred `#zsiqscript` second, rendered into the
  initial HTML on **every page** via the root layout.
- **Chatbot removed, tracking kept (final state):**
  - `app/layout.tsx`: same widget script (it powers visitor tracking/analytics) plus a ready-hook
    that hides the chat button when the widget boots:
    `$zoho.salesiq.ready(function(){ ... floatbutton.visible("hide") ... chatbutton.visible("hide") })`
    (both API generations attempted, wrapped in try/catch).
  - `app/globals.css`: JS hiding alone did not catch the live DOM node, so a CSS suppression layer
    was added targeting the client-inspected element and all known mounts:
    `#zs_fl_chat`, `span.siqico-chat.zsiq-chat-icn`, `#zsiqwidget`, `#zsiq_float`,
    `iframe[src*='salesiq']` → `display:none !important`. The script keeps loading, so visitor
    tracking is unaffected — only the UI disappears.
  - `next.config.js` CSP: Zoho domains re-added for the tracking-only mode — `script-src`
    (`*.zohopublic.in`, `*.zohocdn.com`), `style-src`/`img-src`/`font-src` (`*.zohocdn.com`),
    `img-src` (+`*.zohopublic.in`), `connect-src` (`*.zohopublic.in`, `wss://*.zohopublic.in`,
    `*.zohocdn.com`), `frame-src` (`salesiq.zohopublic.in`).
  - Recommended permanent alternative (told to client): disable the chat button server-side in the
    SalesIQ dashboard (Settings → Widgets → visibility off) — tracking stays on there too.

### 4. Build Stability — Flaky `PageNotFoundError` Root-Caused and Fixed
- Symptom: `next build` failed repeatedly during "Collecting page data" with
  `PageNotFoundError: Cannot find module for page: X` where X changed every run
  (`/_document` → `/_not-found` → `/apple-icon.png`), even after deleting `.next`.
- Investigation ruled out: stale cache, MAX_PATH (LongPathsEnabled=1, no >250-char paths),
  OneDrive sync (project not under OneDrive), missing output files (all present post-failure).
- **Actual causes:**
  1. `npm run dev` (Turbopack) was running concurrently and rewriting `.next` while the webpack
     production build read it — the recurring trigger (dev server had been restarted mid-session).
  2. Machine constraint: 7.5 GB RAM (~1.3 GB free) starving parallel jest-workers.
- Fixes: stop the dev server before building (process discipline — documented here);
  `next.config.js` gained `experimental.cpus: 1` for single-worker collection steps.
- Result: clean production build, 105/105 static pages generated.
