### D. Cart — per-transaction rate limits on `/api/cart/order` + `/api/cart/verify` (commit `2327599`)

Owner request: *"avoid same IP spamming or route attacks — rate limit per transaction trigger."*

A plain per-IP window is the wrong shape for a checkout: one IP legitimately opens many orders (offices, NAT, mobile carriers), while what actually needs braking is spamming the **same cart**, the **same buyer identity**, or brute-forcing **one order's signature**.

- **NEW `lib/cart/transaction-limit.ts`** — `createTransactionLimiter(scopes)` composes the existing `createRateLimiter` (`lib/rate-limit.ts`) into independent named scopes; `check({keys})` fails on the **first** scope over its limit and names it.
  - **Order route scopes:** `ip` **20/min** (burst brake) · `cart` **6/min** (`ip + SHA-256` of the sorted `slug:qty` fingerprint) · `identity` **8 / 5 min** (`SHA-256(email|normalisedPhone)`, across any IP).
  - **Verify route scopes:** `ip` **60/min** · `order` **12/min** (`razorpayOrderId + ip`) — signature brute-force on a single order.
- **Wiring order matters:** `/api/cart/order` checks `ip` **before** parsing, then `cart + identity` **after** customer validation and **before** the Razorpay call, so a spam loop can never create real gateway orders. `/api/cart/verify` checks `ip` before parsing the body, then `order` after the payload is validated.
- 429 responses now carry `scope` + `Retry-After` + `X-RateLimit-Limit` / `-Remaining` / `-Reset` / `-Scope`, so the response itself tells an operator the shape of the attack.
- Fingerprint hashes are **truncated SHA-256 digests used only as in-process map keys** — nothing is persisted or logged.
- `normalizePhone` was made **exported** in `lib/order-status.ts` (was module-private) so the identity fingerprint normalises exactly like the checkout validator.
- Env overrides (documented in `.env.example`): `CART_ORDER_RATE_LIMIT` 20 · `CART_ORDER_CART_LIMIT` 6 · `CART_ORDER_IDENTITY_LIMIT` 8 · `CART_VERIFY_RATE_LIMIT` 60 · `CART_VERIFY_ORDER_LIMIT` 12.
- **NEW `scripts/payment-limit-test.mjs`** — `npm run test:payments` (45 checks: limits, hashing, 429 shape, money-boundary assertions); `npm run test:payments:stress` (`STRESS=1`) for a heavier run. Wired into `test:all`.

### H. Ask Sara homepage promo — desktop "peek + short speech bubble" (frontend, commit `605f436`)

Owner: the Ask Sara tab on the homepage **gets too few clicks** — promote it, but subtly. Scope was chosen by the owner from the option set: **homepage only**, **hover-capable desktop only**, effect = **"peek + short speech bubble"**. One file changed: `app/components/SupportButton.tsx`.

- **Gating — every condition read inside effects, client-only, so the server-rendered markup never contains the bubble (no hydration mismatch):** `pathname === '/'` **and** `matchMedia('(hover: hover) and (pointer: fine)')` (the same guard pattern `CertifiedPartners` uses) **and** not `prefers-reduced-motion: reduce` **and** not already dismissed this session. `sessionStorage` is read only inside that effect.
- **Behaviour:** after **2.5 s** the tab slides out **14 px** (`-translate-x-[14px]`, 700 ms ease-out) and a white bubble with the teal text **"Need help? Get instant AI suggestions"** fades in to its **left** (small tail pointing at the tab); it holds **5 s**, retracts, rests **18 s**, repeats — **max 3 cycles, then it stops** permanently. Constants live at the top of the file (`PROMO_INITIAL_DELAY_MS` / `PROMO_VISIBLE_MS` / `PROMO_GAP_MS` / `PROMO_MAX_CYCLES`).
- **Pause / engagement:** hovering the tab reveals it immediately and stops it ducking away from an intending user (mouse-leave retracts and restarts the loop); a **hidden browser tab pauses it** (Page Visibility API). Opening Sara, clicking the bubble text, or clicking the **✕** stops the promo for the **session** (`sessionStorage['sara_promo_dismissed']` — no cookie, nothing server-side).
- **A11y:** the bubble text and the ✕ are **sibling `<button>`s — never nested** (a button inside a button is invalid). While hidden the container is `aria-hidden` + `pointer-events-none` and both buttons carry `tabIndex={-1}`, so nothing enters the tab order or intercepts clicks when the promo is not shown. `prefers-reduced-motion` users get no promo at all — the tab stays a plain, always-visible tab.
- **Mobile shows nothing** (its media state fails the hover/pointer guard); the tab itself is unchanged and stays flush to the edge.
- **Verification:** `npm run typecheck` exit 0 · `npm run build` exit 0 · headless probe `/tmp/opencode/verify-sara-promo.cjs` **21/21** at 1440 px + iPhone 13 — auto-show ~2.5 s, exact bubble text, bubble left-of + vertically centred on the tab, 14 px peek, no horizontal overflow, auto-retract ~5 s, hover reveal ~370 ms, retract on leave, tab click opens Sara (`input[placeholder="Type your message..."]`), ✕ hides + records the session key, stays hidden > 8 s, survives reload; mobile opacity 0 + flush tab + no overflow; **0 page errors**.
  - **Probe caveat (recorded so it is not re-discovered):** puppeteer's headless shell reports `(hover: none) and (pointer: coarse)` — a *phone's* media state — so the desktop path is unreachable in it and full Chrome is not installed on this box. The probe therefore shims **only the two capability queries the promo reads** (`(hover:hover) and (pointer:fine)` → true, `prefers-reduced-motion` → false) and delegates every other query to the native `matchMedia`; the mobile page is left **unshimmed** (a faithful phone). `page.emulateMediaFeatures` was tried first but `page.emulateMediaFeatures` was tried first but CDP rejects the `hover`/`pointer` features.
