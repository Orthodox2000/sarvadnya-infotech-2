### §1 — What was added

- **NEW `app/components/DiwaliPopup.tsx`** — client component, the whole feature (state, timer,
  storage, markup, styling).
- **`app/(site)/layout.tsx`** — one import + one `<DiwaliPopup />` mount inside `VisitorProvider`,
  next to `<ConsentBanner />`. Mounting it here (not per page) is what makes it "any first-time
  visitor" on every public route with a single maintenance point.

No MongoDB, env var, settings document, `next.config.js` or `globals.css` change.

### §2 — First-visit memory

`localStorage['svd_diwali_2026']` is set to `'1'` **at open time**, mirroring the consent notice's
`svd_consent_notice`. Writing at open rather than at close is load-bearing: a visitor who navigates
away during the 5 seconds must not be shown the card again on the next page — that exact defect was
reported against the cookie card in September (`docs/HISTORY.md` §ConsentBanner v4).

Because `(site)/layout.tsx` is **not** remounted by client-side navigation, the first-visit effect
re-runs on every route change. A `shownRef` in memory stops a second showing in the same tab; without
it, a private-mode visitor (whose `localStorage.setItem` throws) would be blocked by a 5-second card
on **every page** they opened.

### §3 — Timing and dismissal

`AUTO_CLOSE_MS = 5000`, a single `setTimeout` cleared on unmount. Early dismissal is allowed from
three places — the ✕ button, a backdrop click, and `Escape` — because a dialog a keyboard user
cannot leave for five seconds is hostile. The ✕ receives focus on open (`preventScroll: true`).

**Page scroll is deliberately NOT locked.** Locking `body` overflow would remove the scrollbar for
five seconds, shift the layout sideways, then shift it back — a worse jolt than letting the visitor
scroll behind a dimmed backdrop that closes itself.

### §4 — Square fit (the part that had to be right)

One rule, no media queries:

```
aspect-square  w-[min(90vw,80vh,32rem)]     +     object-contain on width/height 1080
```

- 360 px phone → 90vw = **324 px** card, centred with 18 px each side.
- Landscape / short window → 80vh is the limiter, so the card never touches the top or bottom edge.
- Desktop → capped at **32rem (512 px)**, which is the optimizer width in `sizes`.

`object-contain` inside a 1:1 box means the artwork is always shown **whole**: no crop, no stretch,
and even a future non-square replacement is letterboxed rather than silently cut.

`dvh` was considered and rejected: nothing else on this site uses it, and an unsupported unit inside
`min()` invalidates the entire `width` declaration — the card would collapse. `vh` (large viewport)
errs on the small side, which is the safe direction here.

### §5 — Stacking and coexistence

`z-[100002]`: above `ConsentBanner` (`z-[100001]`) and above every existing modal (`z-[100000]`,
`CartDrawer` `z-[9000]`). On a true first visit both the card and the cookie notice can exist; the
card simply covers the banner's bottom-right corner for five seconds, then leaves it alone (the
banner still stays until the visitor dismisses it — that behaviour is unchanged).

### §6 — Deliberate exclusion

`/checkout` and `/demo` are skipped (exact path + prefix). A first-time visitor can land there
straight from a shared link, and a blocking five-second card in the middle of a payment is a lost
order. Both entries sit in one `SKIP_PATHS` array with a comment, so the owner can delete them.

### §7 — Removal (by hand, after the festival)

1. delete `app/components/DiwaliPopup.tsx`
2. delete its `import` line and its `<DiwaliPopup />` line in `app/(site)/layout.tsx`

Nothing else references it. The stale `svd_diwali_2026` key in visitors' browsers is inert once the
component is gone.

### §8 — Verification

The standing single-pass directive was honoured: **no** build, dev/start server, `typecheck`,
`check:*` suite or browser probe was run. Reading the guards: the alt text is descriptive (not a
generic word, not a filename), so `check:alt` is satisfied; no `<h1>` is introduced, so `check:h1`
is unaffected; the popup is not a route, so `check:seo` / `check:schema` are untouched.

## Session 3 — follow-up: wide artwork above `md`

Owner (verbatim): *"for devices abovce md show diwali.png which is wider"*

### §12 — Art direction

| Viewport | Asset | Box |
| :--- | :--- | :--- |
| `< 768 px` (below `md`) | `public/diwali template 2026.png` (1080×1080) | `aspect-square w-[min(90vw,80vh,32rem)]` |
| `>= 768 px` (`md` and up) | `public/diwali.png` (1920×960) | `aspect-[2/1] w-[min(90vw,160vh,56rem)]` |

The swap is a `matchMedia('(min-width: 768px)')` check in an effect with a `change` listener, so a
tablet rotating or a window being resized while the card is open switches to the artwork that fits.
The alternative — two `<Image>` tags toggled with `hidden md:block` — was rejected because both
srcsets ship and `priority` preloads both, so every visitor would fetch two festival images to show
one card.

Height check: the wide box is 2:1, so `min(90vw,160vh,56rem)` wide means `min(45vw,80vh,28rem)` tall —
never taller than 80vh, same ceiling as the square. `object-contain` is kept on both, so an artwork
that does not match its box exactly is letterboxed rather than cropped.

`sizes` for the wide art is `(min-width: 1280px) 896px, 90vw` because the card tops out at 56rem
(896 px) from 1280 px up — otherwise the optimizer returns a file wider than the slot.

## Session 4 — loading speed + optimisation, then document and push

Owner (verbatim): *"perfect, now only thing left is loading speed and optimisation, rest document and push to origin"*

### §14 — The two real costs

1. **The optimizer had to fetch and resize a 2.1 MB PNG** before the first byte of the greeting could
   leave the server (cold `/ _next/image` request per new URL/width/device).
2. **The request could not start until hydration.** The popup is a client component and the
   first-visit flag is in `localStorage`, so the `<img>` does not exist in the server HTML — the
   browser discovered the artwork only after React had run.

### §15 — Fix 1: static, pre-sized WebP

| File | Source | Size | Use |
| :--- | :--- | :--- | :--- |
| `public/diwali-popup-square.webp` | `diwali template 2026.png` (2.1 MB) | **110 KB**, 1024×1024 | `< 768 px` (cap 512 CSS px → 2×) |
| `public/diwali-popup-wide.webp` | `diwali.png` (850 KB) | **139 KB**, 1792×896 | `>= 768 px` (cap 896 CSS px → 2×) |

Built with the `sharp` already in `node_modules`, `fit: 'inside'`, `effort: 6`, quality 78 / 76.
The card renders them with `<Image unoptimized>`: they are already final, and the existing header rule
serves `/public` images `immutable` for a year, so a repeat visit costs no compute at all.

`public/diwali.png` is **not** re-encoded in place: it is embedded on other origins (2026-11-04 rule)
and static files are cached `immutable`, so a same-name overwrite would never reach those consumers.

### §16 — Fix 2: `<head>` preload, first visit only

`app/layout.tsx` now renders a 457-byte inline script in `<head>`. It runs during HTML parse, checks
`localStorage.svd_diwali_2026`, the breakpoint (`matchMedia('(min-width: 768px)')`) and the skip paths,
and appends `<link rel="preload" as="image" type="image/webp" fetchpriority="high" href="…">` for the
one artwork that device needs. The `<img>` then requests the identical URL, so it is one download.

A returning visitor: one `localStorage` read, no link, no fetch, no popup.

### §17 — Why the constants moved to `lib/diwali-popup.ts`

The preload `href` and the `<img>` `src` **must** match exactly; a mismatch silently downloads the
artwork twice. They now come from one pure-constant module imported by the server layout and the
client component. The module also owns the storage key, the breakpoint string, the skip paths and the
script builder.

Not done on purpose: AVIF (`<picture>` doubles the preload-matching surface for ~40 KB), a DPR
`srcset` (a plain `src` is what keeps the preload exact), and server-side first-visit detection (a
cookie read in the root layout would make every route dynamic).

### §18 — Housekeeping

`public/diwali template 2026.png` (2.1 MB) was initially left out of the commit and then
**committed on the owner's explicit request**. Nothing references it at runtime — the popup loads only
the WebP — but it is the *source* of `diwali-popup-square.webp`, and keeping it in git means a fresh
clone or a machine swap can still regenerate the artwork. `public/diwali.png` stays committed for the
cross-origin embeds.

Commit it with `git add "public/diwali template 2026.png"` (the filename has spaces; quote it) and push
to **both** remotes.

### §19 — Verification

Standing single-pass directive honoured: no build, dev/start server, `typecheck` or `check:*` suite.
The generated preload script was syntax-checked with `new Function()`; both WebPs were re-read with
`sharp.metadata()`.

### §20 — Commit + push

Committed on `main` and pushed to **both** remotes per the house rule (§2.5): `origin`

### §25 — Why the images were blocked (and the fix)

The site's global `/(.*)` header sends `Cross-Origin-Resource-Policy: same-origin`, so a cross-origin
`<img>` fails in the browser with `ERR_BLOCKED_BY_RESPONSE.NotSameOrigin` even though the file is public.
`next.config.js` therefore carries a **later** rule (order matters — Next merges `resHeaders[key] =
value`, so a later match wins) that sends `Cross-Origin-Resource-Policy: cross-origin` and
`Access-Control-Allow-Origin: *` for `/email-signature/:path*` and `/TallyCertificate.png`.

Email clients fetch images server-side and never apply CORP, so Gmail/Outlook/Apple Mail were never
affected — this only broke browser previews and pastes. Verified live: `cross-origin-resource-policy:
cross-origin`, `access-control-allow-origin: *`, `cache-control: public, max-age=31536000, immutable`.

### §34 — Follow-up: flush left everywhere, socials under Contact, columns rebuilt as a table

Owner: *"and margin strict left, no padding or margin left"* · *"also social media icon below contact
section"* · *"and even on wider screen, contact section moves to next line"* · *"in sent email"* · *"section

**The fix.** The row is a real `<table>` with two `<td class="sig-col" width="50%">` cells: the split, the
`border-left` divider and the padding are attributes / inline styles, so the columns cannot depend on a
stylesheet. The media query only stacks them below 820px (`display:block;width:100%`), which is why the
signature still reads as one column on a phone.

**Flush left.** sign-off `18px 16px 14px 0` (no `sig-cell` class), brand column `18px 16px 18px 0`,
partner strip / services / legal `… 16px … 0`, and the ≤819px rules zero the left inset on the stacked
Contact cell and `.sig-cell` rows. The desktop Contact cell keeps its 16px so text does not touch the rule.

**Social icons** moved to the end of the Contact column, after the Web row (`margin-top:10px`); the brand
column now ends at the address.
