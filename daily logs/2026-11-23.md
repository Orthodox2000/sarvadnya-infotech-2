## 3. `/api/identify` — smoothen the 36-invocation / 8 s beacon

Owner: *"/api/identify is taking too long with 36 invocations and 8s, smoothen it and make it faster"*.

- **Cause:** a new/stale session waited inline for `ip_cache.findOne` → up to 2.5 s `ipwho.is` fetch → `ip_cache.updateOne` → `visitors.updateOne` (applyGeo) → fire-and-forget rdns (up to 3 s) before returning a bare 204. Cold starts also awaited six serialised `createIndex` calls. `VisitorProvider` already throttles to one beacon/10 s, so the 36 calls are real traffic.
- **Fix 1:** `app/api/identify/route.ts` imports `after` from `next/server` (stable in Next 15.5.29, already used in `/api/cart/order`) and runs geo + rdns enrichment in a post-response callback. The 204 is sent as soon as `recordVisitor()` commits; `applyGeo()` still stamps `geoAt` on null geo so failed lookups are not retried every beacon. Callback is fully caught — visits are never lost.
- **Fix 2:** `lib/visitors.ts` adds a warm-instance `geoMem` Map (TTL-matched, 2000-entry cap, oldest-first eviction) plus `geoInFlight` single-flight so repeat IPs and simultaneous same-IP beacons do zero or one external lookup. Negative results cached for the existing 1 h window.
- **Fix 3:** `ensureVisitorIndexes()` awaits only the unique `sessionId` index needed for upsert correctness; the other five admin/cache indexes warm in the background (they persist in MongoDB and already exist in production).
- No build/dev/typecheck/check suite (single-pass directive §3 — owner did not ask this time; `after` export verified in `node_modules/next/server.d.ts` and via existing `/api/cart/order` usage). Docs: `docs/history/2026-11-23-identify-beacon-fast-path-after-and-warm-geo-cache.md` + one `docs/HISTORY.md` row + this log + tracker row 155. Not committed/pushed yet. Deploy and watch the function chart; geo/rdns still land on the visitor doc, just after the response.
