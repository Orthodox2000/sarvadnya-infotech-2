### §C — ⚠️ `npm run test:all` had been silently red since 2026-10-09 (pre-existing; fixed here)

`scripts/api-test.mjs` decided *"do the admin routes exist in this repo?"* with a bare `fs.existsSync('app/api/admin')`. Git does not track directories, so after the first-party capture routes moved to `app/api/chats` + `app/api/drafts`, **`app/api/admin/chats` and `app/api/admin/drafts/[id]` survived as empty folders** (`git ls-files app/api/admin` = 0 files). `existsSync` therefore returned `true`, the branch flipped to *"admin routes exist → expect 200"*, and the deployed site's **correct 404** was counted as a failure. Because `test:all` is an `&&` chain, **every suite AFTER api-test had not run for four days** (`sara`, `sara-topics`, `cart`, `order-status`, `date-coerce`, `payment-limit`, `seo-links`) — a red suite with nothing real behind it, hiding a green suite that was not running.

Fix: the guard now collects **real `route.(ts|tsx|js|jsx)` files** recursively and only then expects 200 (honest in both repos, and independent of a tidy worktree); the empty leftover directories were removed. `npm run test:api` → 12/12 and the assertion now reads *"GET /api/admin/stats is absent in the public repo (404)"*.

### §E — ⚠️ Correction: the frontend's local `.env` is NOT the production DB

After the commits, a routine end-to-end check **against the live domain** (a step the local verification had not covered) found the seed had gone to the wrong database:

| | Local `.env` (where the seed first went) | Production |
| :--- | :--- | :--- |
| Cluster / db | `sarvadnya.zvdcpsj.mongodb.net` / **`test`** | `ac-1nfykty-…mongodb.net` / **`sarvadnya-infotech`** |
| `news` docs | **24** (20 + my 4) | **20** (my 4 absent) |
| `tally-tss-expiry-meaning` | 11 tags / 5 faqs | 7 tags / 4 faqs |

Evidence it is the deployed DB and not a caching artifact: `https://en.sarvadnyainfotech.com/news/what-is-tally-capital` → **404** with `cache-control: private, no-store, max-age=0` and `x-vercel-cache: MISS`; live `/api/news` → **20** items. The two DBs were otherwise identical (`only in PROD: []`, `only in LOCAL: [the 4 new slugs]`), so nothing else was at risk.

The **deployed frontend reads the same DB the nested admin uses** (`sarvadnya-infotech`) — that is what AGENTS §10 *"Database: Shared"* means; the **local frontend `.env` is the outlier**, which is exactly the discrepancy AGENTS §16 had flagged (`ac-1nfykty…` was recorded as "the nested one", but it is in fact the *production* one).

**Fix applied (owner-approved):** re-ran the seed with the URI overridden — `dotenv/config` never overrides an already-set variable, so:

```bash
MONGODB_URI="$(grep -m1 '^MONGODB_URI=' sarvadnya-advanced/.env | cut -d= -f2-)" node scripts/seed_news.mjs
# → inserted: 4, updated: 2, skipped(unchanged): 15, removed: 0, total 24 docs
```

Then verified **on production**: all 4 article URLs **200** (FAQPage + NewsArticle JSON-LD + company name present), the new *"Is TSS the same as a Tally licence?"* FAQ renders on `tally-tss-expiry-meaning`, and live `/api/news` = **24** including the 4 new slugs.

**Takeaway:** *"24 docs in the local DB"* meant nothing about the live site. A seed is only verified once it is verified on the live domain (or with `MONGODB_URI` forced to the production cluster). The local `.env` was **left untouched** by choice — but note that **every future seed/verification from this machine will hit the wrong DB unless `MONGODB_URI` is overridden or the file is corrected.**
